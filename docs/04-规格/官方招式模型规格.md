# 阶段7.7 官方招式模型规格

> **已取代**：现行内容见[游戏规则](../01-现行规则/游戏规则.md)（2026-10-31，#85）。细节公式、用户原话与当时依据仍以本页为准。

**状态：工作候选规格（已按独立审查修订）。** 本页把用户 2026-10-30 的决定（方向 B，见[招式表现与官方探险队对照](../06-研究/玩法研究/招式表现与官方探险队对照.md)）落成可实现的规则。数值都是工作候选；第 8 节的问题在用户答复前按推荐值实现。

## 1. 目标与边界

**目标（用户决定）：** 招式在迷宫里的射程、目标和效果照官方《宝可梦不可思议的迷宫》探险队（时／暗／空，Bulbapedia 表格中的 MDTDS／BSL 列），取代现有的“强击／直线／保护／推退”四类行为；保护队友改由官方本有的团队招式承担；个别招式以后需要平衡时单独设计。

**执行理解（main 的工作候选，非用户原话）：** 探险队没有的招式参照之后的作品（MDGtI、SMD）；官方都没有的由本作自定；与官方不同之处逐项注明。

**本阶段（7.7a）不做：**

- 不改移动方式：本作是 4 方向网格（`engine.ts` 的 `DIRS`），官方是 8 方向。官方的“可斜穿墙角”在本作没有意义，记为差异。
- 不改普通敌人（`dungeon.ts` 的 `TIERS` 三档）和首领规则。
- 不加命中率：官方招式有命中（如摔打 78%），本作暂时全部命中，因为命中会引入新的随机数，牵涉随机数流与存档（7.4 报告“随机数流共用”）。
- 不加附带的概率状态（灼伤、麻痹、畏缩、中毒、降命中等），这些招式只造成伤害，逐项记为差异。
- 不改招式机清单：`TM_MOVES` 的长度和顺序决定旧存档里随机抽取的含义（`roster.ts` 注释），扩充要版本化，放到 7.7b。

## 2. 射程类别

“无遮挡”指中间格都是可走地面且没有单位。距离用现有的曼哈顿距离（`engine.ts` 的 `distance`，横纵坐标差之和），“周围”用切比雪夫距离（横纵坐标差的较大者）。

| 本作射程 `range` | 官方原名 | 本作判定 |
| --- | --- | --- |
| `front` | Front | 目标与使用者上下左右相邻（距离 1） |
| `front2` | 2 tiles away | 目标与使用者同一行或同一列，距离 1–2，中间无遮挡 |
| `line10` | 10 tiles away | 同一行或列，距离 ≤10，命中射线上第一个单位；官方目标为 All，**队友也会被打中** |
| `around` | 1 tile around user | 使用者周围 8 格内（切比雪夫距离 1）的全部敌人 |
| `room` | Entire room | 使用者站在某个房间矩形内时：同一房间内的全部目标；使用者在走廊、或该局没有房间数据（固定图与 6.4 以前生成的远征）时：切比雪夫距离 ≤2 的目标（本作规则；官方走廊规则未核实） |
| `user` | User | 只作用于自己 |

目标 `target`：`enemy`、`user`、`teammates`（同行队友，不含自己）、`party`（含自己）、`all`（敌我都算）。行动 `{type:'skill',skill,target}` 中，`user` 与 `room` 招式的 `target` 一律填使用者自己的 id，规则据此校验。

首批招式只用到 `front`、`front2`、`user`、`room`。`line10` 与 `around` 一并实现，用测试覆盖。

## 3. 效果

| 效果 | 规则（本作） | 官方依据 |
| --- | --- | --- |
| 伤害 `damage` | 伤害 ＝ `6 + ceil(威力/2)` ＋ 攻击阶段 ＋ 本局等级加成（每级 +1）；普攻仍为 6 ＋ 攻击阶段 ＋ 等级加成。受到伤害时减去防御阶段，最少 1 | 威力取探险队表格的 Base Power；换算公式是本作候选（见下方“强度变化”） |
| 吸取 `drain` | 回复实际造成伤害的 50%（向下取整，至少 1，不超过最大 HP） | 吸取：回复造成伤害的 50% |
| 能力阶段 `stage` | 攻击、防御各 −3…+3。攻击每级使造成的伤害 +1（普攻与招式都算）；防御每级使受到的伤害 −1（最少 1）。跨层（换层）、远征结束时清零；中途加入的伙伴从 0 开始 | 变圆、变硬：自身防御 +1；帮助：房间内队友攻击 +1（官方同时加特攻，本作伤害不分物理特殊，合并为攻击）。“每级 ±1 伤害”是本作换算 |
| 守住 `protect` | 使用后，从本回合的敌方阶段起连续 3 个敌方阶段内，敌人对该单位的攻击（近战、远程、首领）伤害为 0；吹飞撞击伤害不受影响。若该单位上一次行动也是守住，本次使用被拒绝（不扣 PP，给出原因） | 守住：自身，探险队持续 3–6 回合，连续使用易失败（本作改为固定 3 与“连续使用被拒”，避免概率） |
| 反击 `counter` | 使用后，从本回合的敌方阶段起连续 3 个敌方阶段内，相邻敌人每对该单位造成一次大于 0 的伤害（已减去防御阶段），该敌人受到同等伤害；首领一阶段攻击两次则反击两次；被守住挡掉（伤害 0）不触发；撞击伤害不触发 | 追打在探险队里是反击状态（7–12 回合），本作缩短为 3 |
| 吹飞 `blowaway` | 目标沿“使用者→目标”方向逐格移动，最多 10 格：下一格是墙（不可走）则停下，目标受 5 点撞击伤害；下一格有单位则停下，目标与该单位各受 5 点；走满 10 格无撞击。可以经过和停在未揭示的可走格、各类点位上（敌人停在点位上没有效果）。对首领使用吹飞类招式：吼叫、吹飞被拒绝（不扣 PP，沿用 7.3“首领不会被推退”），龙尾只造成伤害不吹飞 | 吼叫、吹飞、龙尾：吹飞 10 格，撞击各 5 点 |

**强度变化（需长测确认）：** 现在强击与直线的伤害固定为 10。按上式，威力 4–7 的常用招式为 8–10，摔打、种子炸弹（16）为 14，电击、吸取（1）为 7、龙尾（3）为 8。整体与现状接近，但不再有远程直线；保护队友的手段也只剩帮助。这会明显改变战斗，第 9 节步骤 4 的长测负责确认。

**新的单位状态字段**（会进存档，规则与存档校验都要认）：`stages:{atk:number,def:number}`、`protect:number`（剩余敌方阶段数）、`counter:number`（剩余敌方阶段数）、`lastMove:string|null`（上一次行动使用的招式 id，用于守住连续判定；该单位执行移动、普攻、使用道具、等待或任何非招式行动后重置为 `null`，所以“守住、移动、守住”不算连续）。缺省值为全 0／`null`。

- **快照（main）：** 用内置浏览器把上表招式（及 7.7b 候选招式）的 Bulbapedia MD 表格存为主 checkout 忽略目录下的 `.artifacts/pmd/moves-<日期>.json`，记录来源页面地址模板（`https://bulbapedia.bulbagarden.net/wiki/<招式>_(move)`）、统一读取时间、所用作品列和每招的原始表格行，并复核第 4 节数值。
- **导入（main）：** 新脚本 `tools/data/import_pmd.py`（仅标准库，先校验快照 sha256，同 `import_showdown.py`）生成 `src/data/pmd-moves.json`：每招 `{range,target,power,effects,source,game,note}`；本作自定的招式 `source:"本作自定"` 并写理由。

## 6. 规则与数据模型的改动

- **招式成为行动单位。** `Skill` 改为招式 id；单位的 `pp`、`maxPp` 以招式 id 为键，`learned` 为招式 id 列表。目标合法性按第 2 节、效果按第 3 节。`SKILL_CN` 改为按招式取中文名（`names-zh.json`）。
- **携带规则。** 仍每只最多携带 2 招（第 8 节问题 1）；“两招行为不能相同”改为“两招不能是同一招式”。
- **名单数据。** `roster.json` 的 `kit` 与 `learnable` 去掉 `behavior`，效果一律查 `pmd-moves.json`。初始招式冻结为现状（不再由生成器按行为挑选）；`tools/data/import_showdown.py` 改为：初始招式取冻结表，`learnable` 只保留招式机能教的招式（首批即 `TM_MOVES`）与初始招式。`tests/core/content73.test.mjs` 锁定名单前 15 条 sha256 的断言随之更新，并在 PR 中说明。
- **冻结的旧对照表。** 迁移需要“旧行为→招式”的对照，所以在代码里冻结一份 `LEGACY_BEHAVIOR_MOVE`：(a) 每个物种现有 `kit` 中“行为→招式”的对应（从现 `roster.json` 生成后写死）；(b) 没有物种的单位（固定图 A／B／C、招募新人 `newcomer`、`scenarios.ts` 中的场景单位）使用固定对照：强击→撞击 tackle，直线→电光一闪 quickattack，保护→守住 protect，推退→吼叫 roar。这类单位保留自己原来的 `maxPp` 数值（例如固定图 B 的守住上限仍是 2），不按第 4 节的 PP 校验。
- **固定图与试验场景。** `engine.ts` 的固定图（`main-invite`、`main-none`）、`newcomer()`、`scenarios.ts` 的场景单位，都按 (b) 改为招式。这会改变阶段 3—4 获准的试验基准（例如 V8 场景原本验证“保护相邻队友”，改后守住只保护自己），属于第 8 节问题 4，由用户决定。在用户答复前按推荐实现（合并门槛见第 9 节）。
- **休整点、PP补剂** 改为按招式 id 补充，数量规则不变。
- **敌人与首领** 不变；招募来的伙伴按其物种 `kit` 取招式。
- **界面** 显示每招的射程与效果（中文），可选目标按射程高亮。

## 7. 存档迁移

**入口顺序。** 现在 `decode` 在迁移之前就拒绝 `rules`／`content` 不等于当前值的记录（`save.ts` 中 `e.rules!==RULE_VERSION` 判断）。改为：`RULE_VERSION` 改为 `trial-rules-2`、`CONTENT_VERSION` 改为 `trial-content-2`；`decode` 先识别旧值 `trial-rules-1`／`trial-content-1`，先执行 7.2 已有的旧迁移（`migrateProfile`、`migrateWorld`，它们读的是带 `behavior` 的旧形状），再对整条记录执行下述招式迁移，把版本改为新值后做现有校验。其他未知版本仍按 7.5 方式拒绝并允许导出原记录。

**要改键的全部位置**（以行为为键的 `pp`／`maxPp`／`learned`，以及 `{move,behavior,pp}`）：

| 位置 | 迁移方法 |
| --- | --- |
| `profile.roster[].learned` | 去掉 `behavior`，保留 `move`、`pp` |
| `profile.rescue[].inst.learned`（救援池） | 同上 |
| `current` 与 `recent` 的 `units` 中的伙伴单位（含 `queue`、`camp`、被交换机送回而仍留在 `units` 的单位） | 有 `moves` 字段：按 `learned[i]`↔`moves[i]` 改键；无 `moves` 但有物种：按 `LEGACY_BEHAVIOR_MOVE` (a)；无物种：按 (b) |
| 每层存档 `dungeon.stored[*].units` 中的伙伴单位 | 同上 |
| `invitations[].unit`（半额邀请快照） | 同上 |
| 敌人身上的 `recruit` 单位（固定图） | 同上 |

新状态字段（第 3 节）在旧记录中补缺省值。`recent` 只用于显示，迁移后不重新结算。迁移后的记录必须通过新版本的完整校验；任何一处无法迁移，整条记录按“不兼容”处理（说明原因、可导出原记录），不做部分迁移。

**测试样本：** 每一类位置各配一个旧版本样本（可复用 `tests/core/fixtures72/` 的样例并补齐固定图、救援池、邀请快照、跨层存档），断言迁移后可读、可继续、往返一致，以及篡改仍被拒绝。

## 8. 需要用户决定的问题（附推荐）

1. **携带几招？** 官方 4 招，本作现 2 招。推荐 **7.7a 先保持 2 招**，4 招以后单独做。
2. **命中率与附带状态何时加？** 推荐 **7.7a 不加**，长测后视战斗是否单调再定。
3. **保护队友的招式从哪里来？** 首批只有帮助。广域防守（小拳石、水跃鱼、大岩蛇、幕下力士可学）、神秘守护等要进入游戏，需版本化扩充招式机清单。推荐 **7.7b 进行**。
4. **固定图与试验验收场景怎么办？** 它们是阶段 3—4 的获准试验基准，按“保护／直线”写成。推荐 **按第 6 节 (b) 对照表改为官方招式，并把依赖旧语义的验收断言改写为新语义**（例如 V8 改为验证“守住保护自己”），在 PR 中逐项列出。备选：保留旧语义作为独立的“试验规则”，但这要同时维护两套招式模型，与“照官方加快开发”相反。

- 步骤 2 期间 `main` 不改分给 `dev` 的文件。`tests/core/soak-bot.mjs` 依赖招式行动的形状，由 `dev` 在步骤 2 中只做最小接口适配，使 `npm test` 通过。
- 步骤 2 的 PR 合并后，`src/core/dungeon.ts` 的数值、`tests/core/soak-bot.mjs` 与 `tools/soak/` 回到 `main`，步骤 4 才开始；其余文件按原分工表恢复。
- 第 8 节问题 4 的推荐方案改动了获准的试验基准：步骤 2 可以先按推荐实现，但其 PR 要等用户答复问题 4 之后才合并。
