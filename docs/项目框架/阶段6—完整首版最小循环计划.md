# 阶段6：完整首版的最小循环

[阶段路线图](从研究到试开发的阶段路线图.md)结束于"试开发复盘"，并说明完整首版要另立计划。本页就是这份计划：把已经跑通的单层片段，扩成"出发→探索→招募→撤离或全灭→回营培养→再出发"的一个完整小循环。

用户在2026-10-30说明了总目标：把 demo 推进到**可试玩的 EA（抢先体验）阶段**，计划定好后自主执行。阶段6 是通往 EA 的第一段，阶段7 补齐 EA 所需的其余内容（见文末）。完整首版应包含哪些内容，以[分阶段范围](分阶段范围与扩展顺序.md)为准；本页决定先做哪一段、怎样验收。

> 状态（2026-10-30）：6.1—6.6 已全部完成并合并（PR #13—#22），结果与遗留问题见[阶段6复盘](阶段6复盘.md)，下一阶段见[阶段7计划](阶段7—可试玩EA计划.md)。

## 起点：阶段5 的实际结论

- **制作者自测已完成**（[记录](阶段5制作者自测-2026-10-30.md)）：所走的代表流程与规格一致；发现的换位草稿错误已修复。
- **独立体验者观察暂不进行。** 2026-10-30 用户决定先不请体验者，并授权自主推进下一阶段。因此"伙伴选择是否有意义""操作是否看得懂""返回是否值得保留"仍是**未验证**的假设，不能写成通过。
- 这些假设随本阶段一起带着走：每个里程碑都要保留观察入口（[观察记录表](../玩法研究/阶段5观察记录表.md)），日后一旦有体验者，就能直接用同一份构建观察，而不必回头补做。

所以进入阶段6 依据的是**用户的决定**，而不是"玩家证据支持继续"。路线图原本列出的三种结果（继续、简化后再测、暂停扩大），这次一个都没有被证据选中。

## 本阶段要回答什么

| 问题 | 本阶段用什么回答 | 仍需体验者回答的部分 |
| --- | --- | --- |
| 单层片段的规则能否撑起多层、随机地图和真实内容 | 程序检查：同一套 R01—R11（R12 是未决项，不是可执行规则） 在随机楼层、跨层与保存恢复下仍然正确 | 无 |
| 一次培养选择能否改变下一次出发 | 能走通"带回招式机→学习→重新配招→下一局用到"的完整链路 | 玩家是否觉得这次培养值得 |
| 真实角色与场景素材能否以个人成本接入 | 素材管线小样：实际花费、步骤数、失败率和可读性自检 | 玩家是否喜欢这种画面 |
| 内容数据怎样从资料变成可玩伙伴 | 首批名单走完"资料→行为映射→素材→遭遇"整条链路 | 新人是否立即有用 |

## 里程碑

每个里程碑都是一个或几个 PR，合并前必须通过对应检查并经独立审查。顺序有依赖关系，但 6.1 和 6.2 可以并行。

| 编号 | 交付物 | 通过条件 |
| --- | --- | --- |
| 6.1 素材管线小样 | 角色、地砖与交互点的取得与转换工具（招式特效要等动作动画决定播放时机，移到 6.4 一起制作）；用真实素材替换单层片段的几何占位 | 单层片段换成真实素材后，原有规则、保存与浏览器检查全部通过；每个素材文件都有来源、许可、生成参数和摘要；画面在 1440 px 与 1024 px 宽下都能分清敌我、交互点与已揭示格 |
| 6.2 内容数据基线 | 选定首批名单与招式，从固定版本的 Showdown 数据生成本作所需字段；写明每种招式映射到哪种本作行为 | 生成脚本可重复运行，结果与固定来源一致；每名首批伙伴都有可用的基础招式组合；映射表有字面测试 |
| 6.3 随机楼层与跨层 | 带种子的楼层生成器、楼梯、跨层与返回（R10），揭示与跟随在随机地形中仍正确 | 同一种子生成同一张图；随机局面下的 V 类不变性测试通过；跨层后保存、关闭、恢复不重放；一张完整普通迷宫具备基础目标、一个继续选择、普通出口与有限战利品 |
| 6.4 真实招募与共享本局等级 | 移动、攻击、受伤动画与招式特效；非 Boss 敌人按概率发出邀请；共享本局等级（工作候选） | 邀请概率与随机状态保存在存档中，恢复不重抽；等级提升不顺带治疗（R07）；局内恢复品可用，HP/PP 消耗与恢复结果正确保存 |
| 6.5 基地与培养 | 名册、三人编队、招式机学习与重配、再出发 | 带回的招式机能学习，下一局实际用到；回营实例保留个人招式库；全灭时普通物资按候选规则处理；回营时的一次性小额休整与基本出发整备按候选规则生效 |
| 6.6 完整循环自测与复盘 | 连续两局以上的自动化流程与制作者自测；更新观察记录表 | 循环中每一步都有程序检查；复盘写明哪些假设仍待体验者验证 |

[分阶段范围](分阶段范围与扩展顺序.md)列出的完整首版内容，本阶段与阶段7 的分工如下：

| 完整首版内容 | 放在哪里 |
| --- | --- |
| 一张完整普通迷宫：基础目标、一个继续选择、普通出口、有限战利品 | 6.3 |
| 恢复：HP/PP 消耗、已有恢复品、一次性小额休整 | 6.4（局内）与 6.5（回营） |
| 基地培养与基本出发整备 | 6.5 |
| 初始二人恢复、全灭时普通伙伴走失、救援订单、基础收入、费用与等待次数 | 阶段7 |
| 商店与交换机等稀有服务点 | 阶段7 |

救援订单、基础收入、费用与等待次数、商店与交换机，属于完整首版的"失败与回归"和"稀有服务点"，放在下一阶段（阶段7）处理。本阶段的全灭只按现有候选处理：普通物资损失、实例结果保存、从基地重新出发。这样每个阶段都能独立成立，不需要先把整套经济做完。

## 内容与素材的工作决定

以下是 Claude 主会话为推进本阶段作出的**工作决定**，随时可以按用户意见更改，不代表最终玩法或发行决定。

### 首批名单

- 规模：御三家 3 种（作为可选主控）加野生 6 种，共 9 种左右。
- 这是阶段6 内对用户提案“主控以历代御三家自选”的**临时收窄**：先用一组御三家打通整条链路，最终仍回到历代御三家自选。[核心玩法](../玩法研究/核心玩法与首版范围.md)中“三代御三家 9 种加野生 3 种，共 12 种”的预算示例保留；扩到更多世代放在阶段7，复盘时一并处理。
- 选择标准：
  1. 覆盖[核心玩法](../玩法研究/核心玩法与首版范围.md)的四种功能配置（守护、射手、牵制、调位）；
  2. SpriteCollab 中所需动作齐全；
  3. Showdown 招式能映射到现有行为。
- 具体物种在 6.2 按上述标准选定并记录理由。世代基准沿用"有限、多样"的原则，本阶段先以第一世代为候选，只因为它辨识度高、素材最齐全；这不是最终时代决定。

### 角色素材：SpriteCollab

用户偏好的 Pokémon Arena 2D 视觉风格，其角色图就来自 [SpriteCollab](https://github.com/PMDCollab/SpriteCollab)（见[视觉规格](../pokemon-arena-2d/视觉样式参考与素材规格.md)）。2026-10-30 核对到的许可要点：

- 社区投稿采用 **CC BY-NC 4.0**，即只能非商业使用，并且必须署名。
- 许多基础角色图的作者标记是 `CHUNSOFT`，即官方游戏原图（例如 0001 号的 `credits.txt`）。这类图片没有经过官方授权，CC 许可也覆盖不到它们。
- 宝可梦本身的知识产权从来不在任何许可之内。

因此：素材只用于私有构建；每个文件都要记录物种编号、动作、作者与许可；公开发布前必须另行决定素材路线。

### 场景、交互点、界面与特效：gpt-image 生成

- 模型：`gpt-image-2.5-sunburst` 用于定稿，`gpt-image-2.5-flare` 用于草稿与批量试验。两者都只支持 `v1/images/generations` 与 `v1/images/edits` 端点，按 token 计费（2026-10-30 主会话读取 [flare](https://developers.openai.com/api/docs/models/gpt-image-2.5-flare) 与 [sunburst](https://developers.openai.com/api/docs/models/gpt-image-2.5-sunburst) 官方模型页，未经独立复核）。同日实测：flare 低质量档生成一张 1024 px 图片约 11 秒、输出 196 个图像 token。
- 只生成原创的环境、物件、界面与特效，**不生成宝可梦角色**。用户允许生成宝可梦模型，这是本阶段主动采用的更严约束，不是用户的禁令。这样可以避免模仿官方角色设计，也不会出现与 SpriteCollab 角色画风不一致的问题。
- 流程：
  1. 写素材卡（用途、尺寸、调色要求、提示词）；
  2. 生成 1024 px 原图，放入被忽略的 `.artifacts/art-gen/`；
  3. 降采样到目标像素格，并量化调色板；
  4. 切图并人工自检；
  5. 采用的成品放入工程，并在素材清单里记录模型、质量档、提示词、token 用量、后处理参数与 SHA-256。
- API key 只从主 checkout 被 Git 忽略的 `.env` 读取，不复制进任务 worktree，不打印，不写进日志、提交或报告。

### 数据：Pokémon Showdown

固定一个提交，只导入本阶段用到的字段（物种、属性、能力值、招式及学习方式），生成本作的 JSON，并记录来源提交。生成物和映射表一起提交；原始仓库不放进本仓。Showdown 仓库为 MIT 许可（2026-10-30 经 GitHub API 核对），这只覆盖其代码，不覆盖宝可梦数据本身的知识产权。本仓目前为私有仓库；一旦公开，已提交的素材与生成数据即构成公开分发，必须先另行决定。

## 测试与验证方式

- **完全自主测试，不请体验者。** 包括规则单元测试、独立断言（由 `mercury-acceptance` 从规格编写）、Windows Edge 浏览器检查，以及主会话在内置浏览器中的真实键鼠自测。
- 画面可读性由主会话截图自检，结论写明这是制作者判断，不是玩家证据。
- 随机内容一律带种子，测试固定种子；存档必须保存随机状态（R11）。
- 继续区分"亲自运行""复用"和"自述"三类证据，Linux 结果不代替 Windows。

## 工作方式

- 2026-10-30 用户授权：自主推进与规划；合并 PR、删除废弃 worktree 和分支不需另行询问；可以使用 gpt-image 生成图片。
- 仍保留的约束：
  - 所有改动走任务分支加 PR，不直写 `main`；
  - 涉及代理规则、权限、存档或玩法规则的改动，合并前做独立审查；
  - 实现与验收的分工见 [Claude 作业方式](../工作环境/Claude作业方式.md)。
- 目标是可试玩的 EA 阶段；计划定好后自主执行，不逐步询问。
- 危险操作（运行来源不明的代码、改动系统或全局环境、可能破坏用户数据的批量删除等）不直接在本机执行，改用云环境或其他隔离方式。下载的图片与数据文件只当数据处理，不执行。
- 在 OpenAI API 上使用 gpt-image 属于已授权的使用；“新增付费服务”指其他新服务。
- 公开发布、联系体验者、扩大网络权限、新增其他付费服务，仍需用户另行决定。

## 主要风险

| 风险 | 处理 |
| --- | --- |
| 宝可梦知识产权与官方原图 | 只做私有构建；逐文件记录来源与许可；公开发布另行决定 |
| 生成素材画风不统一 | 先做一组地砖、物件、特效的小样，与 SpriteCollab 角色同屏检查，通过后再批量生成 |
| API 费用 | 草稿用 flare 低质量档；素材清单记录每次 token 用量。用户在2026-10-30说明该 API 额度总共只有 50 美元，因此预算按整个项目分配：阶段6 不超过 15 美元，单批不超过 2 美元，其余留给阶段7（按官方页每百万图像输出 token 30 美元、图像输入 8 美元、文本输入 5 美元估算）。生成脚本维护累计费用账本（`tools/art/usage-ledger.json`，从首次端到端测试调用记起），预计超出上限时拒绝调用；账本按 API 返回的用量估算，与 OpenAI 用量页不一致时以用量页为准并修正账本；草稿一律先用 flare 低质量档，确认方向后才用高质量档定稿 |
| 构建体积增大 | 6.1 起记录主脚本与素材总大小；需要时按需加载 |
| 玩家假设始终未验证 | 每个里程碑保留观察入口；复盘明确列出未验证项 |

## 阶段7：从最小循环到可试玩的 EA

阶段6 完成后，按复盘结果编制阶段7 的详细计划。预期内容：上表列为“阶段7”的失败与回归、稀有服务点；更多世代的御三家与名单扩充；Windows 版（Electron）封装与私有试玩包；新手引导、设置与存档管理；性能与构建体积。达到 EA 可试玩状态不等于公开发布，发布方式仍由用户决定。EA 的通过条件在阶段7 计划中定义，至少包括：从全新存档开始能连续游玩多局而不需要开发工具，存档跨版本可用或可迁移，Windows 与网页构建都经过实测。
