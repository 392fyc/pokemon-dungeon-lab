# KB 维护规则

本库（仓库的 `docs/`，同时是 Obsidian vault）遵守 Mercury `kb` 包的通用约定（`.mercury/packs/kb/docs/kb-conventions.md`）。本页只写本项目在通用约定之上的专属规则。规则编号 K1、K2…，改动规则时在同一个 PR 里更新本页并在[决策登记](../03-决策/决策登记.md)登记。

为什么要这些规则：代理靠搜索和链接找文档，搜索看不到“状态”标签。过时的文字只要还留在库里，就会被搜到、被当成现行规则来读。所以本库只保留现行的内容：过时或错误的文档、规则和决策行直接删除。以前的版本在 Git 历史、Issue 和 PR 里，需要时用固定提交的永久链接引用。

## K1 分级结构

| 目录 | 放什么 | 一句话判断 |
| --- | --- | --- |
| `01-现行规则/` | 游戏规则核心页与主题页（游戏现在怎样运作）、本页 | “现在是这样” |
| `02-进度/` | 唯一的进度页；`计划/`（进行中的里程碑计划与规格） | “做到哪了、正在改什么” |
| `03-决策/` | 决策登记 | “谁在什么时候定了什么” |
| `05-制作流程/` | 数据与素材的现行流程和登记 | “内容怎样进游戏” |
| `06-研究/` | 仍在使用的调查、纸面推演和参考作品研究 | “我们查到了什么” |
| `07-工作环境/` | 代理与 lane 怎样工作 | “谁怎样干活” |

- 根目录只放入口 `README.md`。每个目录都有 `README.md` 索引，列出本目录每篇文档及其状态。
- 新文档放进最贴切的目录，并在同一个 PR 里给该目录索引加一行。不新建一级目录；确有需要时先改本页。
- 不设归档目录。旧材料需要引用时，用固定提交的永久链接：`https://github.com/392fyc/pokemon-dungeon-lab/blob/<提交SHA>/<路径>`。
- 文件名按主题起，日期放在末尾（如 `研究汇总-2026-10-27.md`）。不以日期开头，因为检查脚本会把数字开头当作排序编号，判定为重复。

## K2 状态

状态只写在目录索引的“状态”列，只有两种：

- **现行**：有效，可作为工作依据。研究目录里的“现行”指仍是未实现系统（如无尽迷宫、探险队等级）的设计依据，不表示规则已定。
- **草稿**：正在一个未合并的任务里写，合并前不作依据。

没有第三种状态。文档过时或被证明错误时，在造成这件事的那个 PR 里删除它，同时删除或改写所有指向它的链接。

## K3 读取顺序

代理开工时按这个顺序读，读到够用为止，不扫全库（下方例外除外）：

1. 入口 [README](../README.md)；
2. [进度](../02-进度/进度.md)；
3. [游戏规则](游戏规则.md)核心页全文，再全文读与任务相关的主题页（各节在哪一页，见核心页的“各节摘要”和“改哪里要读哪页”）；
4. [决策登记](../03-决策/决策登记.md)中与任务相关的行；
5. 任务 Issue 里“KB to read”列出的计划或研究；
6. 需要以前的细节（例如某条决策的用户原话）时，按决策登记“来源”列的固定提交链接或 Issue 去查。

例外（适用范围同 K8）：要回答游戏规则的问题、给出规则或设计结论、或写入规则与决策时，用 Read 读完[游戏规则](游戏规则.md)核心页全文、本页全文和相关主题页全文；拿不准涉及哪几页时读全部主题页，不按关键词或编号筛选行。会话被压缩后，交结论前重读一遍。派发子代理时，在任务说明里写明要读哪些全文。（D-20261103-09、D-20261111-06）

为什么分层：分层前的游戏规则单页约 64 KB，长会话里一次读不全，“整页全读”就落空。核心页小到必读得完，主题页按 G 节分，每页读得下。

仓库根 `AGENTS.md` 的读取说明指向这里。

## K4 随任务更新

每个 PR 都按改动类型更新对应文档，并在 PR 描述里写一行 `KB:`，列出更新或删除了哪些文档，或写“KB: no impact”并说明原因。PR 还要引用它的 Issue（`Refs #N`），否则 `guard.ps1 pre-merge` 会拒绝合并。

| 改动 | 同一个 PR 里要做的 |
| --- | --- |
| 改了游戏规则或数值（包括 main 的工作值） | 改游戏规则对应主题页的条目（核心页摘要随之更新）；在决策登记加一行，删掉被推翻的旧行；删除或改写因此过时的研究段落 |
| 里程碑合并或状态变化 | 改[进度](../02-进度/进度.md)的里程碑表、已知问题和下一步 |
| 新里程碑开工 | 在 `02-进度/计划/` 写计划或规格，状态“草稿”；用户原话写进任务 Issue |
| 计划或规格合并且实现完成 | 把结论收进游戏规则和进度页，登记决策，然后删除这份计划或规格 |
| 做了自测或长测 | 证据写进 PR 描述；结论（例如最新长测的全灭率）写进进度页；不单独存记录文件 |
| 新研究 | 放进 `06-研究/` 对应子目录，并在索引加一行 |
| 用户做了新决定 | 在决策登记加一行，决定者写“用户”；原话写进对应 Issue 或 PR 正文，来源链接到那里 |

### PR 必须完整

一个 PR 合并之后，不应该再需要另一个 PR 替它补记录。否则每合并一个 PR 就要再开一个 PR 写进度，永远写不完。

用户定的两条（D-20261107-01）：

- **PR 必须完整。** 这个 PR 该做完的事不留到下一个 PR，合并后不留待补的记录。
- **禁止补记 PR。** 不开只为补记上一个 PR 进度的 PR。

下面是 `main` 定的执行细节，用户可改（D-20261107-02）：

- **范围。** 上表要求的进度、规则、决策、索引都算，并写成合并之后成立的样子。例如第 3 批的 PR 自己就把进度页写成“完成”，写上自己的 PR 号。
- **不写本 PR 自身的过程状态。** 不写本 PR 的“候选”“待审”“尚未合并”和合并提交 SHA，因为这些在合并后就过时，或者合并前无从得知。写 PR 号就够了。PR 号要开 PR 后才知道，开 PR 后补一个提交写上，这仍是同一个 PR。
- **合并后才发现漏项。** 放进下一个有实际内容的 PR 一起改，并在 PR 描述里写明。
- **审查按阻断处理。** 审查 PR 时，漏掉上表的收尾算阻断问题，改完才合并。

### 基础系统照定式做

背包、学招式、招募、奖励选择这类基础系统，先查成熟做法（用户点名探险队和 Poke，再加同类游戏），再照着做，不凭感觉发明。在 PR 里写明参考的是什么，这一条是 main 的落实。（D-20261107-06）

画面不放解释性句子（D-20261108-01），这是画面规则，写在[迷宫界面主题页](规则-迷宫界面.md) G13.5。

## K5 计划与规格的生命周期

草稿（开工时写在 `02-进度/计划/`）→ 合并（实现完成）→ 结论收进游戏规则、进度页和决策登记 → 删除。

游戏规则只写结论，条目注明来源决策编号。删除后需要看规格细节时，按决策登记里的永久链接查当时的版本。

## K6 决策

- **决定者分两种：**
  - 用户：原话保存在来源（Issue、PR 或仍现行的文档；已删除的文档用固定提交链接）；
  - main：代理按授权定的工作值，用户可随时改。

  不能把代理的推导写成用户决定。
- **新决策推翻旧决策：** 删除旧行，新行不写旧编号（旧编号已不在工作树里）。编号不复用，删掉的编号空着。

## K7 写作

- 简体中文，按费曼方式写：外行也能看懂，定义术语，给出例子或证据。
- 区分以下几类内容：
  - 用户决定与代理推断；
  - 实测与纸面推算。
- 库内用相对 Markdown 链接（`[文字](../01-现行规则/README.md)`），不用 `[[wikilink]]`，不以 `/` 开头。提到 `docs/` 以外的仓库文件，写代码格式的仓库相对路径。
- 代理直接编辑任务 worktree 中的文件，与代码一起走 PR。Obsidian 只用于浏览主 checkout，见[Obsidian 使用说明](../07-工作环境/Obsidian使用说明.md)。

## K8 查证与依据

适用于本项目的 Claude：本机主会话和它派出的子代理。Codex 与 Codex 云按各自的流程。（D-20261103-09；“立刻更正”见 D-20261111-06）

- **先查证再回答。** 回答里的每个事实性说法，都要在本次回答前用一手来源核实：读文件、运行命令、查 `gh` 或 API 的返回、读用户原话。包括规则与数值、文件和代码的现状、PR 与 Issue 的状态、工具和会话能做什么、另一个会话或代理的进度。记忆、会话摘要、上一轮的结论和其他代理的报告只当线索，用之前要重新核对。
- **结论附依据。** 交给用户的结论标出依据：规则编号（G、K）、决策编号、`文件:行`、PR、Issue 或提交、命令输出，或用户原话。
- **查不到就说查不到。** 指不出依据的判断不写成结论，单独列为“待查”，写明还缺什么、打算怎样查；不能用推测填空。
- **说错了立刻更正。** 发现之前的回答没有依据或有错，在下一次回答里主动指出并更正。

## K9 交付前独立审查

适用范围同 K8。规则或设计结论、计划与规格、改动 `docs/` 的 PR，交给用户或合并之前，先由独立审查代理（Claude 上用 `mercury-reviewer`）核对，包括只在聊天里交付的规则或设计结论：

- 是否违反游戏规则、本页或决策登记；
- 是否有用户没要求、由代理自行添加却写成用户决定的内容（K6）；
- 每条结论是否有依据（K8）。

审查发现的问题改完再交付；交付时写明审查结论。（D-20261103-09；计划、规格与 PR 的范围和“写明审查结论”见 D-20261111-06）

## K10 检查与整理

- 每个改动 `docs/` 的 PR 都要通过：

  ```
  python -B -X utf8 .mercury/packs/kb/scripts/kb_check.py docs
  ```

  它检查索引、状态和每一条库内链接。规则是否正确由审查负责：审查者要核对改动与游戏规则、决策登记是否一致，库里留着已被改动推翻的文字算作问题。
- **每个里程碑收尾时整理一次：**
  - 游戏规则核心页超过约 10 KB、或单个主题页超过约 25 KB 时删减或再拆（这是 main 的工作值，用户可改，D-20261111-06）；
  - 进度页的“已知问题”逐条核对，已解决的删掉；
  - 删除已完成的计划和规格。
