# 二维迷宫引擎决策

2026 年 10 月 25 日，用户授权代理根据调查作出引擎决策。当前决定：采用 **Phaser 4 + TypeScript**，以网页作为第一种开发验证载体；需要 Windows 独立程序时，复用游戏代码并使用 Electron 封装。正式首发平台仍待产品讨论。本轮只完成选型，没有安装引擎、创建游戏工程或实现玩法。

当前官方发行页与 npm 注册表均为 **Phaser 4.2.1**；这是本次选型的版本基线。实际开工时核查是否有适用修复，并锁定依赖，不跟随浮动版本自动升级。[官方发行](https://phaser.io/download/release/v4.2.1)、[npm 元数据](https://registry.npmjs.org/phaser/latest)

## 决策依据

本项目的主要复杂度来自随机地牢、招式与特性适配、伙伴行为和跨局存档。用户希望保留网页与 Windows 两种可能，采用二维像素角色和有限多样阵容。当前没有三维场景、主机发行或必须使用特定可视化编辑器的要求。

Phaser 官方将其定位为面向浏览器的二维框架，使用 JavaScript 或 TypeScript，桌面分发需要额外工具。这与我们的网页试玩目标直接匹配。Godot 同样能够完成目标；选择 Phaser 是对数据处理、浏览器验证和迭代方式的权衡，不是认为 Godot 缺少二维能力。[Phaser 定位](https://docs.phaser.io/phaser/getting-started/what-is-phaser)

| 需要完成的事 | Phaser + TypeScript | Godot + GDScript | 对本项目的判断 |
| --- | --- | --- | --- |
| 网页试玩 | 直接运行网页程序 | 导出 WebAssembly 与 WebGL 2 程序 | 网页作为首个验证载体时，Phaser 路径更直接 |
| Windows 独立程序 | 增加 Electron 封装、桌面存档与打包 | 引擎直接导出 Windows | Godot 在这一项更省步骤 |
| 多方向角色、格子地图 | 帧动画和 TilemapLayer | AnimatedSprite2D 和 TileMapLayer | 两者均可；动作、偏移点和特效仍要整理 |
| Showdown 资料处理 | Node 导出器与游戏逻辑都可用 TypeScript | Node 导出 JSON，再由 GDScript 读取 | Phaser 便于共用类型与校验；Godot 导入 JSON 也可行 |
| 云端检查 | 规则在 Node 检查，画面在浏览器检查 | 可无界面导出，再检查网页产物 | 两者均可自动化；当前环境已有 Node 与浏览器 |
| 人工编辑内容 | 配置文件为主，可另用可视化工具 | 集成场景与动画编辑器 | 若以后依赖大量手工场景编辑，Godot 的价值会提高 |

Godot 当前稳定版为 4.7.2；4.8 仍在测试阶段。网页导出需要 WebAssembly 和 WebGL 2，默认单线程导出可以避开多线程所需的跨源隔离要求，不能笼统说“Godot 网页必须设置特殊响应头”。[版本档案](https://godotengine.org/download/archive/)、[网页导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)、[Windows 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_windows.html)

## 怎样吸收已有研究

### 招式与数据

借鉴 PokéBonk 的分层方式：来源数据、可用内容名单、共用攻击行为、单招参数覆盖和特殊效果分别管理。不会照搬它的实时冷却、强化数值或融合门槛。见[招式适配研究](../参考项目/pokebonk/招式适配与融合系统.md)。

Showdown 官方 Node.js API 当前不直接支持浏览器。因此采用构建阶段导出：固定 Showdown 修订和世代，提取本游戏需要的物种、招式、特性描述与学习资料，生成 JSON。地牢中的射程、墙体遮挡、友伤、队伍行动和资源消耗另行定义。不能把含有战斗回调的招式源文件直接转 JSON，就宣称全部效果已实现。[Showdown 官方包说明](https://github.com/smogon/pokemon-showdown/blob/master/sim/README.md)、[Dex 文档](https://github.com/smogon/pokemon-showdown/blob/master/sim/DEX.md)

建议让地图生成、行动结算、伤害、物品和存档规则保持独立于画面；Phaser 负责角色显示、输入、镜头、音效和演出。这样可用固定地图种子与行动记录重现问题。可重现性需要我们正确管理随机数和结算顺序，不是使用 TypeScript 就自动获得。

### 用户喜欢的像素风格

Arena 2D 的参考重点是多方向角色、脚底阴影、地面层次和招式演出。Phaser 的帧动画与地图层可以承载这些视觉元素；最终效果取决于图像、动作偏移、比例与特效制作，不由引擎名称保证。SpriteCollab 的方向、动作与脚底基准仍需转换和检查。见[视觉参考](../参考项目/pokemon-arena-2d/视觉样式参考与素材规格.md)、[素材流程](../../05-制作流程/角色素材与招式特效流程.md)。[Phaser 动画](https://docs.phaser.io/phaser/concepts/animations)、[TilemapLayer](https://docs.phaser.io/api-documentation/class/tilemaps-tilemaplayer)

Phaser 在线文档部分页面仍带旧版本示例，当前 TilemapLayer API 页标注 4.1.0。实际写代码时以锁定版本的类型和发行说明核对接口，尤其是渲染与特效，不混用 Phaser 3 的自定义管线。

### 桌面交付与测试

Windows 版本选择 Electron 作为封装路径，复用网页游戏逻辑与资源。它仍然需要桌面存档位置、窗口输入、离线资源、安装包和更新的具体实现与验收；不会因为网页可运行就自动完成桌面发布。[Electron 分发说明](https://www.electronjs.org/docs/latest/tutorial/distribution-overview)

现有 Codex Cloud 只验证过工具链、临时网页点击与截图。本轮没有测试 Phaser 的实际 WebGL 场景、性能或 Windows 程序。以后用代表性场景检查显示与性能，Linux 云端承担规则和浏览器检查，本机 Windows 承担原生程序验收。见[环境说明](../../07-工作环境/REA与CodexCloud.md)。

## 其他候选与重新评估条件

PMDO / RogueEssence 有现成地牢体系和素材处理代码，值得继续作为行为与格式参考。PMDC 公开构建说明列出 Windows、Linux 和 macOS；本轮没有核实可直接使用的网页输出路线。因此不把它当作网页项目的直接起点，也不声称它技术上永远不能移植。[PMDC 构建说明](https://github.com/PMDCollab/PMDC/blob/master/README.md)

Unity 没有在当前需求中显示出必须采用的独占能力，本轮不引入另一套编辑器和发布流程。

若用户把目标改为 Windows 原生优先、依赖大量人工场景编辑，或要求三维 / 主机发行，应重新比较 Godot 等候选。若当前方向不变，后续按 Phaser 路线推进，无需反复重开同一选型。
