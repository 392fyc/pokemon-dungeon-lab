# 营地存档模型规格

**状态：工作候选规格。用户决定见第 1 节；第 3 节以后是 main 的落实方式，已按一轮独立审查修订。** 本页取代 [玩家操作与中断恢复](玩家操作与中断恢复.md) 第 5–7 节中“迷宫内保存与恢复”的部分；那几节的其余内容（操作约定、邀请、撤离表达）不变。

## 1. 用户决定（2026-10-30，对话中）

**确认敌人行为时，用户答复原话：**

> 做原版贴近，但不用考虑存档问题：我们只有在回到营地后才会存档，结算收获。如果在迷宫图中退出，会自动读档到进入迷宫前在营地的状态。

**之后 main 又问了两个问题，用户都选了推荐项。以下是选项标签，不是原话：**

| main 的提问 | 用户所选 | 该选项的说明 |
| --- | --- | --- |
| “在迷宫里快要全灭时关掉页面，就能回到出发前——不丢伙伴、不付救援费。这样可以吗？” | “可以，中途退出不罚 (推荐先这样)” | — |
| “远征打完到了结果页，还没按‘回到营地’就关了页面——这趟的收获算不算？” | “结束即自动结算存档 (推荐)” | 撤离或全灭的那一刻就结算并存档，结果页只是展示；关页面不会丢收获；全灭时伙伴走失也立刻记下 |

**main 的理解：**

- 一次远征，从出发到结束（撤离或全灭），在存档里**不可分割**：要么在结束那一刻整体结算并保存，要么什么都不留下。
- 远征结束前因任何原因离开（关页面、刷新、浏览器崩溃），重新打开时回到出发前的营地状态，本次远征作废，**没有惩罚**。用户知道这允许“快全灭时退出”来避免损失，并接受。
- 第二个选项把用户原话中“回到营地后才会存档”细化为“远征结束即存档”。结果页之后回到营地只是切换画面，不再写入。

## 2. 为什么这样更简单（从目标推导）

- **现有做法：** 每完成一个处理点，就把整个迷宫世界（`Envelope.current`）存一次。为此要做三件事：
  - 校验每一种中间阶段（`playing`、`invitation`、`exit`、`transit`）；
  - 处理迷宫内保存失败时的冻结与重试；
  - 保证读档后与关闭前逐项一致。
- **新规则下：**
  - 迷宫世界只存在内存里，存档只描述营地。
  - 迷宫内的新状态都不进存档、不用校验，也不会因读档产生不一致。这些新状态包括：7.8 的敌人睡眠、漫游目标、追击记忆，以及队友方针的临时修改。

## 3. 规则（main 的落实方式）

1. **存档内容：** 只存营地档案（`profile`）和格式元数据。迷宫世界（`World`）不写入持久存储。
2. **写入时机：** 开新游戏（`beginNewGame`）与导入存档（`importRecord`）照旧写入；除此之外，游戏过程中只有两种写入：
   - **营地操作：** 学招式、带招式、编队、付救援费。这四种就是 `src/core/base.ts` 的营地操作，照现有方式各自保存。
   - **远征结束：** 撤离或全灭成立的那一刻，把本次远征的结果一次性结算进营地档案，然后保存一次。
     - 结算内容沿用现有 `settleRun`：带出的物品与金钱、招募的伙伴、走失的伙伴、带出或丢失的招式机等。
     - 现有代码是在按“回到营地”时调用 `settleRun`（`save.ts` 的 `returnToBase`），改为在终局成立时调用。
3. **出发时不写入：**
   - 现有的 `depart` 会立即写一次存档，其中包括从账户扣出本次携带的钱包。改为不写。所以存储里留着的始终是出发前的营地状态。
   - 下面这些都只在内存里，中途离开时全部作废，账户金额因此保持出发前的数值：
     - 出发时扣出的钱包；
     - 迷宫内商店的购买（`engine.ts` 的 `buy` 指令，要求领队站在商店格上）；
     - 交换机送回的招式机。
4. **中途离开：**
   - 远征结束前离开，重开后读到的是出发前的营地档案。
   - 出发时不写存档，重开时程序无从得知“上次有过远征”，所以不在重开时提示。改为在出发确认处说明一次：“远征途中离开（关闭、刷新）会回到出发前的状态，本次远征作废。”
5. **结果页：** 只展示已经保存的结算结果。按“回到营地”只切换画面，不写入。
6. **保存失败：**
   - 营地操作保存失败：沿用现有的“画面保留、可重试、禁止后续改变状态的操作”。
   - 远征结束那次保存失败：停在结果页并显示可重试；重试只重新保存同一份结算结果，不重复结算。保存成功之前不能回到营地。
7. **导出／导入：** 只导出、导入营地档案。
8. **最近结束记录：**
   - 营地画面现有的“查看最近结束记录”读的是 `envelope.recent`，也就是整个已结束的迷宫世界。
   - main 的工作候选：删去这项功能，结果只在结果页展示一次；`recent` 字段随之删除。
   - 若以后需要回看，再另定一个只含结果摘要的营地字段。
9. **只读写迷宫世界的接口：**
   - 包括 `newTrial`、`start`、`resetAfterExport`。
   - 它们只供开发者场景与测试在内存中构造世界，不再读写持久存储。
   - 开发者菜单与固定场景（`scenarios.ts`、`?dev=1`）同样改为直接在内存里构造。

## 4. 旧存档（main 的工作候选）

- **带进行中远征：** `current` 不为空、阶段不是 `ended`。丢弃这次远征，保留营地档案，等同于“中途离开”。
- **带已结束但未回营地的远征：** `current.phase==='ended'`。为与用户的“结束即结算”一致，读档时先对它补做一次 `settleRun` 结算，再丢弃迷宫世界，不让这趟收获丢失。
  - 补结算前必须先完整跑一遍现有的旧档读取流程：`validWorld` 校验、`migrateWorld` 与 `migrateLegacyMoveState` 迁移、`BOSS_HISTORY` 首领旧数值核对。校验不通过的按“没有营地档案”同样处理（保留原字节，导出后重置），不结算。
  - 两条同时符合时（例如旧式无基地远征：已结束、又没有营地档案），“没有营地档案”一条优先，不结算。
- **没有营地档案：** 例如 `trial-rules-1` 的旧档、开发者场景的档、旧式无基地远征的档。沿用现有“损坏记录保留、导出后明确重置”的处理：保留原始字节供导出，然后回到标题页开新游戏。
- **版本号：** 存档格式因此改变，需要升级版本号。按 [多lane并行协作](../工作环境/多lane并行协作.md)，版本号变更须开同时带 `lane:main` 和 `lane:dev` 标签的协调 issue，并由用户在 Codex 中确认。

## 6. 顺序

建议先实施本规格，再实施 7.8。7.8 的敌人睡眠、漫游与追击记忆都是迷宫内状态；存档模型先简化，7.8 就不用为它们设计存档字段与校验。

## 7. 验收

- 远征进行中关闭或刷新页面，重开后营地档案与出发前逐字节相同，账户金额未扣。
- 撤离或全灭成立后立即保存。在结果页关闭再重开，营地档案已含本次结算，例如带出的金钱、新伙伴、走失的伙伴。
- 营地操作保存失败可重试；终局保存失败停在结果页可重试，不重复结算。
- 旧存档：进行中的远征被丢弃；已结束未回营地的远征补做结算；没有营地档案的按“保留原字节、导出后重置”处理。
- 导出、导入只含营地档案。
