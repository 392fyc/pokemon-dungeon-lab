# 参考解析方法

用户 2026-11-02 把“解析参考作品”定为长线任务。要积累的东西包括：

- 解析方法论；
- 素材产出；
- 美术选型；
- 宝可梦素材流水线。

点名的对象是 PDMN 和 pokemonAutoChess（PAC）。宝可梦作品里的素材和招式实现，也可以作为解析对象。

本页写的是怎样做一次参考解析、成果放在哪里。具体结论在 [06-研究/参考项目](../06-研究/参考项目/README.md)。

## 1. 先定问题，再看代码

每次解析都从本作当前要做的决定出发，写成可回答的问题。

- **例子**：2026-11-02 的问题是“同一地形相连时怎样变换样式”“视野怎样画”“底部栏放什么”。这三个问题分别对应地形规格、视野表现和 #143。
- 不做“把整个游戏看一遍”式的漫游。

参考作品的做法只是一个已经能运行的假设。写进本作建议前，要说明：

- 它解决了本作的哪个问题；
- 照搬时依赖什么条件；
- 哪些条件本作不具备。

## 2. 证据分类

每条结论标明属于下面哪一种。不同种类不能互相顶替。

| 种类 | 含义 | 例子 |
| --- | --- | --- |
| 维护方自述 | 官网、更新日志、制作人员页 | “迷宫图块来自原版” |
| 运行观察 | 亲自玩、截图 | 水沟四角是圆的 |
| 源码 | 公开客户端或开源仓库，带文件摘要与行号 | `Oc` 去掉无效斜角位 |
| 推断 | 由命名或结构推出，未直接验证 | “DTEF 是 SkyTemple 的交换格式” |

## 3. 两类对象，两种做法

**公开网页客户端**（PDMN、PokéBonk 等）：

1. **捕获**：用 curl 或脚本下载入口 HTML，再按 import 字符串递归下载全部 JS 分块，存进 REA 工作台的 `<作品>/<日期>-<构建号>/raw/`。
   - 同时写 `capture-manifest.json`，给全部文件记录 URL、字节数、SHA-256 和时间。
   - 下载的内容只当数据读，不执行。
2. **排版**：用 REA 依赖里的 Babel 解析后重新打印，结果放进 `derived/`。这一步只解析语法，不导入、不运行目标代码。
3. **定位**：用关键词检索找入口，例如 `make.tilemap`、`putTileAt`、`destination-out`、`createRadialGradient`，再沿调用逐段阅读。
   - 压缩后的变量名（如 `d6`、`Oc`）只在同一构建内有效，换构建就要重新定位。
4. **REA**：用 `analyze-javascript-application` 补模块关系和调用图。
   - 2.7MB 的单文件会超过 300 秒的默认上限，要用 `--source-path` 限定分块，并加 `--analysis-timeout-ms` 放宽时限。
   - REA 的自动图通常只覆盖一部分，结论仍要人工核对源码。2026-11-07 对 PDMN 和 PokéBonk 的打包分块，它识别出的模块数都是 0，语义图只作定位，结论不依赖它。
   - 本机 REA 目录 `D:\Project\rea` 的 `dist` 比源码旧，直接运行会报错。不改那个目录，用官方包 `npx -y rea-agents@6.8.0`，从工作台目录运行。
5. **运行观察**：在内置浏览器里玩到需要的画面再截图。
   - 不注册账号，Cookie 只选必要项。
   - 画面缩放会让点击坐标偏移，优先用键盘操作。

**开源仓库**（PAC 等）：

- 交给 `dev` lane 的 Codex 或本机子代理克隆，按固定提交读源码。
- 每条结论附固定提交的永久链接和行号。
- 不运行会联网下载或改环境的安装脚本，例如 PAC 的 postinstall 会下载音乐。

工作台位置：

- 本机工作台是 `D:\Project\Pokemon\Pokemon_REA_Workbench\`，不入库，按“目标/日期-构建号”分目录；
- 云端另有 REA 环境 `rea-research-lab`（见固定提交 d03ef51 的 `docs/06-研究/REA辅助研究/`）。

## 4. 写成研究文档

研究文档放在 `docs/06-研究/参考项目/<作品>/`，一个作品一个目录，截图也放在里面。文件名写主题，不重复作品名；同一主题有新构建时更新原文档，不另开带日期的新文档。每篇依次包括：

1. **问题与结论**：先给结论和一个具体例子。
2. **证据与边界**：读了什么、没读什么；文件摘要；本机工作台路径。
3. **机制**：按数据从哪来、怎样计算、怎样上屏的顺序讲，术语第一次出现时要定义。
4. **素材来源与许可**。
5. **对本作的建议**：标明是建议、不是决定。
6. **待定事项**：需要用户拍板的选项。

建议一旦被用户采纳，就写进决策登记与现行规格。研究文档保留分析过程，不重复现行规则。

## 5. 许可边界

- **代码**：只学思路，独立重写，不复制。PAC 是 GPL-3，PDMN 没有公开许可。
- **素材**：
  - 原作提取的图块和特效不进本作；
  - SpriteCollab 按 CC BY-NC，仅用于私有构建，逐文件记录作者；
  - 字体按各自许可（例如 OFL）评估后才能用。
- **生图**：用 OpenAI 生成原创素材，按[素材管线](素材管线.md)的账本与上限执行。API key 只从主 checkout 被忽略的 `.env` 读取，不进入云端。

## 6. 从解析到素材

解析结论变成素材时，按这个顺序：

1. **定格式**：例如地形用 DTEF 的 3 段 × 47 形状 × N 变体。
2. **定生产方式**：程序生成、生图加像素化，或许可明确的社区素材（例如 SpriteCollab 角色，仅私有构建）。
3. **在游戏截图里比较**：小批量试做，把 2—3 个方案放进同一张游戏截图，给用户比较（D-20261101-27）。
4. **形成产线**：选定后写进[素材管线](素材管线.md)，逐文件记入素材清单。
