# 参考项目的制作与发布管线

研究由 REA-research-lab 云环境完成，主会话整合。九项目矩阵中，深入研究覆盖自有 Auto Chess mod 与 PokéBonk 历史构建，其他七站受云端网络策略限制。本报告是部分覆盖的静态研究，不能写成九项目都已完成深挖。

证据位置和固定链接见[76 项证据索引](参考项目—管线证据索引—2026-10-27.md)。主会话另外核对自有 mod 的素材处理说明、龙舞效果实现和构建入口替换代码，并匹配本地 PokéBonk 主包摘要、复核 PNG 角色与 GLB 道具路径；其余观察由云端报告与原始证据提供，不声称全部重新运行。

实际采集时间：2026-10-27 **02:25:21–02:28:34 UTC+9**，对应 2026-10-26 17:25:21–17:28:34 UTC。逐请求时间、URL、HTTP结果和摘要见 `sources.json`。

本轮只读取公开源码和既有发布样本，没有执行游戏、目标代码、构建、素材转换或游戏API请求；没有安装、升级、运行doctor、提交、推送或评论。

**二、自有mod：2D精灵从素材到运行时**

实际源码链为：

```text
SpriteCollab本地仓库的AnimData.xml、动作PNG
→ 按动作、普通/闪光、方向裁帧
→ durations.json、delays.json、单帧PNG
→ TexturePacker生成PNG/JSON图集
→ 复制到项目资源目录
→ assetpack打包并压缩图集JSON
→ Phaser按编号懒加载、还原图集
→ 按动作、方向、逐帧时长注册动画
```

证据：

- `edit/README.md:15–37`明确列出裁帧、TexturePacker、精简、复制和肖像处理步骤。
- `edit/add-pokemon.ts:264–307`读取`AnimData.xml`，从`HitFrame`之前的累计帧时长生成攻击延迟。
- 同文件`:330–407`按元数据尺寸裁帧，`:470–510`复制时长、延迟和图集，`:614–641`定义TexturePacker CLI参数。
- `edit/assetpack/.assetpack.js:1–60`定义资源入口、输出、Phaser3导出和版本后缀；`:150–205`把图集压成`i/s/a`结构。
- `app/public/src/game/components/pokemon.ts:1631–1749`还原帧矩形，加载图集JSON及PNG，两者使用`?v=<pkg.version>`。
- `app/public/src/game/animation-manager.ts:24–141`按36 FPS基准换算逐帧时长，区分动作、朝向、闪光和影子；缺少Eat动画时改用Sleep。

这证明的是**外部现成2D精灵的加工流程**，不是3D角色制作流程。源码能证明存在TexturePacker使用脚本，不能证明作者使用什么绘画软件，也不能据此估算每只角色的制作工时。

可复用机制包括统一编号与帧命名、同时生成动画时长和命中延迟、按需加载、缺图兜底。真正成本在动作覆盖、方向、时长、资源权利及版本同步；“换一张图”并不等于完成角色接入。

**三、自有mod：莱希拉姆“青焰”的完整技能路径**

```text
Reshiram基础属性与BLUE_FLARE技能ID
→ AttackingState选敌、检查PP和状态
→ castAbility分派策略
→ BlueFlareStrategy计算并排队伤害
→ 广播Transfer.ABILITY
→ 客户端检查simulation.id
→ 查询特效表、加载帧并播放
```

具体事实：

1. `app/models/colyseus-models/pokemon.ts:7099–7112`定义莱希拉姆`maxPP=100`、`range=3`、`skill=BLUE_FLARE`。
2. `app/core/attacking-state.ts:18–83`优先保留旧目标，处理最低生命目标、混乱与重新寻敌；满PP、未沉默且不受特定噩梦限制时施法。
3. `app/core/abilities/abilities.ts:16416–16450`按技能ID取策略，处理禁止施法道具、暴击资格，并触发`OnAbilityCastEffect`。
4. `ability-strategy.ts:1–40`负责扣PP、计施法次数和广播。`abilities.ts:85–118`的青焰策略计算基础量`50 + 火系羁绊等级×10`，加入250ms延迟命令，对目标当前格及邻格敌人调用`handleSpecialDamage`。这是伤害处理输入，不能直接当成实战最终扣血。
5. `pokemon-entity.ts:1909–1962`向观看同场模拟的客户端广播；`pages/game.tsx:535–545`接收消息；`battle-manager.ts:873–900`按`simulation.id`过滤。
6. `abilities-animations.ts:1499–1510`将青焰映射到`projectile({scale:3})`；`:298–365`检查特效帧和动画，创建、播放并销毁精灵。

边界是：共享入口、PP、广播和事件钩子可以复用；青焰的羁绊加伤、延迟与邻域伤害属于专用策略，投射物视觉又属于另一张客户端表。**伤害与特效不是同一个物理碰撞对象**，复制技能ID和数值不等于完整实现技能。

静态推导的耦合点包括技能ID、坐标、模拟身份和资源帧名。延迟伤害会读取目标后续位置；特效缺项或消息到达时已切换模拟，都可能使视觉与战斗结果不同。本轮没有运行验证这些情形。

**四、自有mod：噩梦奖励的发牌、选择、生效和继承**

实际路径：

```text
回合命令
→ prepareNightmareRewardsForStage
→ 里程碑/特殊到期判断
→ 生成最多三个候选
→ Player Schema同步
→ React选择器发送选择/刷新
→ 服务端按鉴权UID校验
→ 写入拥有奖励并清空候选
→ 创建战斗模拟时安装奖励效果
```

主要证据：

- `app/rooms/commands/game-commands.ts:1727–1742`触发奖励准备。
- `app/rooms/game-room.ts:2746–2867`检查阶段并生成候选，排除已拥有、已选及互斥奖励。
- 同文件`:2868–2942`实现每槽最多一次刷新和未见奖励偏好。
- `player.ts:123–138`定义同步数组和计数器。
- `game-nightmare-reward-picker.tsx:24–106`显示候选并发送选择/刷新；`NetworkStore.ts:209–226`发送命令。
- `game-room.ts:580–608`使用`client.auth.uid`；`:2944–2986`再次校验模式和候选合法性。
- `game-commands.ts:2027–2050`对未选择的候选自动随机挑选。

奖励并非完全由数据表表达：元数据定义层级、类型和说明，普通抽取先按阶段权重选层级，再从该层可用奖励中均匀选。15阶段B/A为85/15，25阶段为20/80，35阶段A/S为50/50；候选耗尽可能返回空，因此不能承诺永远生成三项。

特别需要纠正一个容易产生的判断：`nightmareRunSeed`存在，**不代表普通模式奖励完全确定**。`game-room.ts:2497–2577`中的种子哈希选项只在沙盒强制层级路径使用；普通路径落到含`Math.random`的抽取函数。

以`DRAGON_DANCE`贯穿：

- `types/nightmare.ts:174–188`将其定义为A级团队被动，英文说明只写开场满PP。
- `game-room.ts:2018–2045`在模拟启动前安装奖励效果。
- `core/nightmare-rewards.ts:69–103`不仅开场填满PP，还给每个队伍实体添加周期效果：每10秒遍历队伍，给存活且未复活中的队友补满PP。
- `pokemon-state.ts:967–980`推动周期效果，`effects/effect.ts:173–198`扣计时、触发并重置。

因此真实执行行为比该英文说明更多；`v1Implemented=true`也只是字段，不能代替验收。

可复用的是元数据、服务端候选校验、刷新次数、事件效果和快照记录。耦合则涉及回合阶段、Schema、实体生命周期、PP条件和专属状态。

一个具体静态成本：龙舞为N个实体各安装一个遍历全队的回调，同周期可能形成N次全队扫描，即O(N²)工作；实际性能没有测量。周期效果遇到很大的`dt`也只触发一次后重置，不会补发所有漏掉周期。

`player.ts:311–341`的`transformPokemon`保留原ID和`nightmareReward`并维护绑定字段，证明**这个替换路径**考虑了奖励继承；不能泛化为所有进化、合成、出售路径都安全。Schema同步与局内日志也不能证明服务器重启后的存档恢复。

**七、PokéBonk历史包：十万伏特的定义到执行**

`moves.json`的`id=85`为`thunderbolt`：电系、special、power=90、麻痹及原始概率10。

静态路径：

```text
A.load建立id/key索引
→ Vv把thunderbolt映射为chain模式
→ Hv转换基础数值、状态概率和特殊覆盖
→ Kv保存等级、计时、升级mods
→ 更新循环逐技能调用castMove
→ py合成角色/技能倍率
→ chain选敌、逐跳伤害、视效、音效
```

定位：

- 模式参数：`[754749,754952)`，基础`dmg=13、cd=1.4、count=3、area=8`。
- 十万伏特映射：`[758100,758500)`。
- `Vv/Hv`转换：`[768350,770400)`。
- `py`执行入口：`[775990,777000)`。
- 连锁执行：`[784925,785610)`。
- `aimTarget`：`[1488898,1489776)`。

选敌不是原样使用数据的`target`字段：先考虑有效锁定目标，手动模式按视角评分；自动模式优先近处治疗/护盾敌人，再取视线可达最近者，最后回退最近者。

chain首击搜索范围14，无目标时短延迟重试；后续每跳选未访问的邻近敌人，伤害按`0.9^跳数`衰减。Hv把原始10%麻痹概率转换成0.16，再受mods等影响，不能照搬原作数值解释本游戏。

视效按key查询：十万伏特有专用双层电弧与Bolt粒子处理`[425980,426390)`，缺少专用link时使用通用电弧/光束；声音也有专用路径`[59500,59870)`，缺项则通用zap兜底。

可复用机制是“数据→通用攻击模式→实例mods→统一执行”；边界是专用视听、特殊覆盖、元素反应仍散落在代码里，不能认为整个招式库只靠JSON即可制作。

**八、PokéBonk历史包：元素反应和结算恢复**

元素反应定位`[736000,736985)`：

目标湿润且受到电系命中时，消耗湿润状态，对半径9内其他湿润敌人最多追加12次电击，追加基础量为0.8倍并带麻痹概率，原命中返回1.5倍系数。追加攻击带`noReact`；伤害入口在`[728740,729150)`检查这个标记，阻止继续递归反应。反应key另有0.25秒节流。

可复用的是状态组合、传播上限和防递归。耦合包括敌人索引、状态数组、同一run时间、combat与vfx；全局反应key节流也可能使不同位置的同时反应互相抑制。以上为静态控制流，没有进行平衡或联机验证。

结算恢复定位`[2198874,2203460)`：

```text
startRun请求/runs，固定key重试
→ checkpoint分批发送
→ finishRun先存本地pending
→ POST结算
→ 成功清除；可重试错误退避重发
```

pending仅保留最近5条，checkpoint按最多300条分批；本地心跳和`navigator.locks`辅助识别仍活跃的页面并恢复中断局。离线票据可能没有id且不计ranked，不能承诺离线进度一定保存。

客户端把部分409按已保存处理，但没有服务端源码，不能因此证明服务端完全幂等、防作弊或数据库事务正确。

另有按账号命名的本地构筑计划，载入时过滤、去重、限额`[1581050,1582450)`。它证明的是**构筑计划保存**，不是完整战斗存档。profile默认补齐也不等于任意旧档无损迁移。

**九、PokéBonk历史包：发布与兼容**

旧boot包动态导入主游戏、语言、样式及单独three chunk，失败发出`pokebonk:boot-failed`。news包直接标明`0.8.47 / mvnpa0xv`，并维护资源版本表：

```text

data路径 → 按具体JSON追加?v
未列出项 → 回退构建号
```

news包定位`[165100,166660)`。这证明分包、延迟导入和资源版本寻址，不能证明构建命令、CI平台或HTTP缓存配置。

HTTP客户端在主包`[2194700,2196600)`发送`X-Client:2`，解析服务器`update`标记并触发升级回调。说明静态浏览器包之外还有协议、票据与结算后端；不能将其发布过程简化为上传HTML。

可复用点是版本化资源清单、升级提示、结算恢复队列。相应成本是旧客户端共存、旧资源保留、API兼容、票据时效、有限本地队列及回滚。后端实现和实际发布流水线仍不可见。

**十、对后续制作的复用判断**

| 机制 | 可学习价值 | 必须承担的工作 |
|---|---|---|
| XML到2D图集 | 统一动作、时长、命中延迟 | 资源权利、动作覆盖、编码/解码一致性 |
| 服务端技能＋客户端特效表 | 战斗与视觉可分开维护 | ID、坐标、时间及缺项检查 |
| 通用攻击模式 | 批量派生招式 | 特例、视听和状态组合验证 |
| 数据化奖励＋事件效果 | 复用抽取、校验、刷新与效果挂钩 | 阶段、实体重建、文案同步 |
| 2D角色＋3D道具 | 按表现需求分配资源复杂度 | 节点名、材质、缓存和生命周期契约 |
| 多层版本与结算恢复 | 降低资源更新和断线损失 | 资源、协议、存档共同升级与回滚 |
