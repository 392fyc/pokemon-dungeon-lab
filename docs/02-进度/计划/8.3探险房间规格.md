# 8.3 探险房间规格

状态：草稿（main 的云端工作者起草，等本机 main 定稿；定稿前不作 dev 的开工依据）。依据：[v0.1 纯肉鸽计划](v0.1纯肉鸽计划.md)第 3、7 节；用户决定 D-20261101-10（四类探险房间、进门前有标识、战斗房大、任务与道具房小），数值授权 D-20261101-12；地图依 [8.2地图规格](8.2地图规格.md)。挑战房的开始方式由用户决定（“站上石碑才开始”，[PR #124 评论 6557199822](https://github.com/392fyc/pokemon-dungeon-lab/pull/124#issuecomment-6557199822)）。本页其余数字是工作值：main 已在 [PR #124 评论 6556993021](https://github.com/392fyc/pokemon-dungeon-lab/pull/124#issuecomment-6556993021) 定下 Q2—Q6 与原 8.2 Q7 的大部分（main 工作值，用户可改，D-20261101-12），本稿已按此修订；第 9 节列出已定的和仍待用户决定的问题。

可行性数据来自 [`tools/verify/rooms-83.mjs`](../../../tools/verify/rooms-83.mjs)（在 8.2 参考生成器 `tools/verify/map-feasibility.mjs` 的地图上分配探险房间），1000 种子 × 3 层，Linux（Node v24.22.1），基于 main `0e62257`。

## 1. 目标与范围

在 8.2 的大地图上，把一部分普通房间变成“探险房间”，让玩家有理由偏离去楼梯的最短路：进挑战房打一场换奖励，进道具房拿一件补给。8.3 做完整的挑战房与道具房，以及四类房间共用的框架（类型分配、门口标识、房间状态）；委托房与祝福房只做框架，内容在 8.4。

**不在本里程碑**：委托与祝福的内容（8.4）、探险队经验（8.5）、机器人进房间（8.6）。

## 2. 术语

- **探险房间**：被指定了类型的普通房间。类型四种：挑战、委托、祝福、道具。
- **候选房间**：可以被指定为探险房间的房间＝不是到达房、不是下楼梯所在的房间、不是首领房、不是定点敌人守的房间。
- **大房间**：宽≥6 且高≥5（至少 30 格），能同时容下队伍 3 人与 4 只敌人并留出走位；**小房间**：其余。
- **门格**：房间边缘上、与房外地面相邻的格。一间房可能有几段门（被几条通道连着）。

## 3. 规则（玩家看到的）

1. **数量与类型**：每层 2 或 3 间（各 50％）。每个名额按权重抽类型：挑战 35、委托 30、祝福 20、道具 15（计划第 3 节）。已有挑战房或这一层没有大的候选房间时，挑战从这次抽取的权重里去掉。第 3 层同样配置，首领房另算。
2. **挑战房用大房间**，其他三类优先用小房间；没有小的候选时用大的。
3. **门口标识**：门格被揭示时，门格上显示这间房的类型标记；完成后（挑战清场、道具拿走、委托或祝福处理过）标记变暗。玩家进门前就知道房间类型（D-20261101-10）。挑战房的门口标识在挑战进行中显示为“封闭”。
4. **挑战房**：
   - **挑战石碑**：挑战房中心放一块挑战石碑（中心格；房间宽或高为偶数时取中心偏左上的那一格，同 8.2 的 `center`）。石碑格可以站、可以穿过，不放拾取物，敌人不在上面生成。石碑有三种状态：**未挑战**（亮）、**进行中**、**已完成**（暗）。
   - **开始**（用户决定，PR #124 评论 6557199822）：主控站在石碑上“交互”，用掉这一轮的行动；轮末主控仍活着且仍在石碑上，挑战才成立（与 G3.3 下楼梯请求的成立条件相同），否则取消、行动不返还。**不交互就不会开始**：队伍可以照常穿过挑战房，石碑保持“未挑战”。
   - **封门**（挑战成立的那一轮轮末）：房间外紧贴门格的通道格变成临时墙；房间外的存活同行按队列就近移到房间内的空格（同 G3.4 的入场办法）；然后在房间里离队伍最远的空格生成 3 或 4 只（各 50％）本层敌人：物种、等级、HP 按本层规则（G7.1—G7.4，乘难度倍率），醒着，行为同普通敌人。封门时已在房间里的普通敌人也算本场敌人。石碑变为“进行中”。
   - **进行中**：门封着，谁都进不来、出不去；房间外的敌人照常活动。挑战房里的敌人照常给经验、掉钱（G9.6）、参与招募抽签（G8.1）。
   - **结束**：房间里的敌人全部倒下的那一轮，轮末处理完（经验、进化、邀请）后开门，并给一份奖励（第 4 节）。队伍在挑战房里全灭就是普通全灭。
   - 每间挑战房只能挑战一次：开门后石碑变为“已完成”，再交互被拒绝并说明原因、不消耗行动。
5. **道具房**：房间中心放一件道具，二选一（各 50％）：
   - **大树果**：对自己或相邻同行使用，HP 回满；满 HP 时拒绝。
   - **全员 PP 补剂**：使用者一次行动，在场所有存活同行每招回 1 PP（不超过上限）；全员 PP 都满时拒绝。
   拾取同现行树果（主控站上去“取得”），进背包，只在本局。名称是工作名，界面措辞由 dev 与用户商定（D-20261101-20）。
6. **委托房、祝福房（8.3 只做框架）**：生成、门口标识、房间中心一个交互点；8.3 里交互时拒绝并说明“尚未开放”，8.4 填入内容（main 定，Q2；这样 8.3 到 8.4 地图与随机序列不变）。
7. **房间状态只在本局**（`World` 内），不进存档；现行存档不保存进行中的远征（8.2 规格第 7 节），所以不需要迁移，也不需要改版本号。
8. **其余点位（原 8.2 Q7，已定）**：v0.1 的地图**不再生成 G（第 1 层基础目标）和交换机**；T、休整点、商店照常生成（第 9.1 节）。两者的代码保留给 v0.2，只是 v0.1 的远征不再放置。

## 4. 挑战房奖励池（起草者提议，main 定稿）

清场后从下表按权重抽一项，当场给出：

| 奖励 | 权重 | 内容 | 理由 |
| --- | --- | --- | --- |
| 货币 | 30 | 钱袋 ＋40 | 约等于 3—4 只敌人的掉落（每只 5—15）；够买两个树果或半张商店招式机，不会让商店失去意义 |
| 道具 | 25 | 道具房道具中的一件（大树果或全员 PP 补剂，各 50％），直接进背包 | 打完一场最需要的是回复 |
| 伙伴邀请 | 15 | 对本场敌人中的一个物种（本场第一只敌人）发一份邀请，走现行邀请流程（G8.2 半额快照、G8.3 满员替换） | 与击倒招募相同的流程，不新增规则 |
| 招式机 | 15 | 从现行招式机池抽一张，进本局持有；只有击败首领才带回（G9.8） | 和 T、首领掉落一致；探险队经验“带回招式机每张 ＋2，上限 2”（计划第 5 节）会受它影响 |
| 祝福 | 15 | 祝福三选一（8.4 的祝福池）；**8.4 合并前**抽到祝福改给货币 ＋40（main 定，Q3），8.4 合并时恢复 | 计划第 3 节列了祝福 |

奖励类型在封门时就用独立随机序列定下（不受战斗过程影响，同一种子可复现），开门时公布。

**期望值（纸面）**：按第 5 节的数据，63％ 的层有挑战房，一局 3 层期望约 1.9 场挑战，即每局约 0.6 次货币、0.5 件道具、0.3 份邀请、0.3 张招式机、0.3 次祝福；外加每场 3.5 只敌人的经验与掉钱（每局约 ＋6.7 只敌人）。这比现在每局的击杀数（能力值伤害长测里 tactical 平均 7.8 只）多出将近一倍，8.6 要把它算进首领击败率与全灭率的校准。

## 5. 可行性验证（1000 种子 × 3 层，Linux）

命令：`node --experimental-strip-types tools/verify/rooms-83.mjs --seeds 1000 --out .artifacts/verify/rooms-83-1000.json`。

| 检查 | 结果 |
| --- | --- |
| 候选房间数（每层） | 5 间 946 层、6 间 1051、7 间 744、8 间 259；最少 5 间，够放 3 间探险房 |
| 2—3 间是否都放下 | 3000/3000（2 间 1496 层、3 间 1504 层） |
| 候选中的大房间（每层） | 0 间 87 层（2.9％）、1 间 781、2 间 1407、3 间以上 725 |
| 实际类型占比 | 委托 34.4％、挑战 25.4％、祝福 23.7％、道具 16.5％（挑战“每层至多 1 间”把它从名义 35％ 压到 25％） |
| 有挑战房的层 | 1904/3000（63％），三层大致相同（636／651／617） |
| 挑战被去掉（没有大候选） | 87 层，原因都是大房间被到达房、楼梯房或定点敌人房占了 |
| 非挑战房借用大房间 | 52 层（没有小候选时） |
| 挑战房面积 | 30—48 格，中位 40 |
| 挑战房入口段数 | 1 段 303、2 段 944、3 段 551、4 段 104、5 段 2；门格 2—18 个，中位 6 |
| 其他探险房面积 | 12—48 格，中位 20 |
| 探险房离到达点的路径 | 中位 18 步（5—77） |

**解读**：

1. 数量没有问题：每层至少 5 间候选，2—3 间总能放下。
2. 大房间基本够：97％ 的层至少有一间大的候选。剩下 2.9％ 没有挑战房，是定点敌人或楼梯先占了大房间；main 定不为此加规则（Q4）。
3. **挑战房多数有 2—3 个入口**，不少还是通道穿过的“过道房”。所以挑战改为站上石碑交互才开始（用户决定，Q1），去楼梯的路上穿过挑战房不会被迫开打。
4. 封门要堵住的门格中位 6 个、最多 18 个，所以“封门”定义成把房外紧贴门格的通道格变成临时墙，而不是改房间内部。

## 6. 生成与状态（dev 实现要点）

1. **独立随机序列**：类型分配、挑战敌人、奖励、道具各用自己的序列（按 `(seed, level)` 派生），8.2 的地图、敌人、拾取物都不变（G7.8）。参考算法见 `tools/verify/rooms-83.mjs` 的 `assignRooms`。
2. **状态**：每间探险房记 `{room 下标, type, state}`，`state` 为 `idle`／`sealed`／`cleared`（挑战）或 `idle`／`done`（其他）。封门格列表、本场敌人 id 列表、奖励类型随状态存放。挑战敌人 id 用 `c{层}{a—d}`，不与普通敌人的 `w{层}{a—f}` 冲突。
3. **封门与寻路**：临时墙对敌我寻路、视野（G4.4 与 D-20261101-19 的走廊视野）都按墙处理；开门后恢复为地面。
4. **跨层**：探险房间只在本层；离开这一层后状态冻结（8.1 起只能向下，回不来）。

## 8. 测试与验收条件

dev 的新测试（独立重写检查逻辑），各跑 ≥200 种子 × 3 层：

- **R1** 每层 2—3 间探险房间，全部是候选房间；每层挑战房至多 1 间，且是大房间。
- **R2** 同一 `(seed, level)` 两次生成逐字节相同；8.2 的地图、敌人、拾取物与 8.2 合并时的固定回归值逐项相同（新增内容不改变旧序列）。
- **R3** 类型占比在 3000 层上接近第 5 节（委托约 34％、挑战约 25％、祝福约 24％、道具约 16％，以参考实现的同算法结果为准，不放宽成宽范围）。
- **R4** 门格被揭示前不显示类型；揭示后显示；完成后变暗。
- **R5** 主控在石碑上交互、轮末仍活着且在石碑上：通道上紧贴门格的格变成墙；房外存活同行全部入房；生成 3 或 4 只醒着的本层敌人，不在石碑格上，不与队伍相邻（除非房间放不下）；封门前已在房里的普通敌人计入本场；石碑变为“进行中”。交互后主控在轮内倒下或被吹离石碑：挑战不成立，行动不返还。
- **R6** 封门期间：任何单位不能穿过封门格；寻路与视野把它当墙。
- **R7** 最后一只本场敌人倒下的那一轮，经验、进化、邀请处理完后开门并发奖；奖励类型与封门时预抽的一致；同一间房不能再次开始。
- **R8** 挑战房里全灭＝普通全灭（G9.7），结算不受影响。
- **R9** 道具房：拾取进背包；大树果回满 HP、满 HP 拒绝；全员 PP 补剂给在场存活同行每招 ＋1、全满拒绝；拒绝时不消耗、不占行动（同现行背包物品）。
- **R10** 委托房、祝福房：生成并显示标识；交互被拒绝并说明“尚未开放”，不消耗行动。
- **R11** 不交互穿过：队伍沿通道穿过挑战房（多个入口进、另一个入口出），全程不封门、不生成挑战敌人，石碑保持“未挑战”，门口标识不变。
- **R12** 石碑状态：未挑战→进行中→已完成；已完成后再交互被拒绝并说明原因、不消耗行动；门口标识在进行中显示“封闭”、完成后变暗。
- **R13** v0.1 地图：≥200 种子 × 3 层上，没有一层生成 G（`goal`）或交换机（`exchange`）；T、休整点、商店照常出现（商店仍按 G3.2 的概率）；除 G 与交换机外，其余点位、拾取物、敌人与 8.2 合并时的固定回归值逐项相同。

合并前（dev 交证据）：`npm run check`、`npm test`、`npm run test:acceptance`、`npm run build`、`npm run test:browser`、`tools/soak/balance.mjs` 四种打法各 30 种子（普通档）。8.6 之前机器人不进探险房间，所以长测只能证明没有回归，不能衡量探险房间的平衡；挑战房的平衡在 8.6 测。
