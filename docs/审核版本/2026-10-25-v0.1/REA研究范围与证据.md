# REA 辅助研究范围与证据 v0.1

目的：把“制作我们的游戏”和“理解外部实现”分开。REA 是分析工具；需要研究一个外部实现，不代表必须使用 REA，更不代表需要先逆向整款游戏。

## 工作分类

| 问题或材料 | 所属路线与首选方法 | REA 是否需要 | 对首批的影响 |
| --- | --- | --- | --- |
| 人数、成长、救援、费用、撤离和无尽选择 | 游戏路线：按目标比较候选与体验 | 不需要；工具不能替玩家决定是否有趣 | 游戏自身的待裁决事项 |
| Showdown 的物种、招式和学习资料 | 游戏路线：读取固定修订的公开数据，自己定义地牢适配 | 不需要反编译数据库 | 需要数据基线与有限名单 |
| SpriteCollab、PMDO 格式、RogueEssence 导入器源码 | 游戏路线：公开文档、源码与素材小样 | 通常不需要；文档冲突先查解析代码 | 需要可用素材和显示验证 |
| Arena 2D 的像素样式、地面层次、动作表现 | 游戏路线：公开截图、视频与素材来源 | 目前不需要；没有选定可分析客户端 | 视觉参考可独立使用 |
| PokéBonk 普通招式的参数、条件与执行路径 | REA 路线：先复核公开客户端静态定位，必要时追踪调用关系 | 可辅助；简单文本已足够时直接停止 | 可减少适配试错，不阻塞首批 |
| PokéBonk 伙伴/招式实例的创建、使用和保存恢复 | REA 路线：确定构建与最小文件集，再查状态读写 | 有适配价值的逆向候选 | 只影响具体参考结论，不替代本作存档设计 |
| PokéBonk 融合后的继承、换槽和存档 | REA 路线保留现有静态观察，待本作采用相关机制再深挖 | 可辅助，但现阶段低优先 | 本作未选融合，不是前置 |
| 原作 PMD 的已公开符号、结构和反编译源码 | 游戏路线先读现成资料；需要深入函数时向 REA 路线提问 | 现成资料能回答时不需要 REA | 用作机制参照，不自动照搬 |
| 原作 PMD 尚未解析的函数或格式 | REA 路线：选定作品/地区/修订/问题与样本后，做最小验证 | 条件满足后可辅助；不能承诺直接解析任意 ROM | 当前无具体样本，不是首批阻碍 |
| 作者内部编辑器、团队分工、真实工时与留存 | 公开采访/开发记录/实际数据研究 | 仅凭逆向不能证实 | 不以代码量、版本数代替生产效率 |
| REA 工具本身升级、MCP 注册与分析引擎安装 | 沿既有维护授权单独处理 | 工具维护，不是游戏研究交付 | 只有实际研究遇到依赖时再处理 |

## REA 当前可据以判断的能力

2026-10-25 只读核对本机源码：REA 6.7.0，提交 `475f09d5ca4f854cbc634074d5534717d58c6664`，工作区无本地改动。本次没有重新安装、构建、运行 doctor 或分析任何游戏目标。

- 本地 [README](D:/Project/rea/README.md) 与[JavaScript 产物指南](D:/Project/rea/docs/javascript-artifact-reconstruction.md)说明：可静态分析指定目录或 ASAR，输出模块、导入、来源位置与覆盖限制，不执行目标代码。
- [应用工作流](D:/Project/rea/docs/javascript-application-workflows.md)列出 `analyze_javascript_application` 之后的 `trace_application_feature`、`trace_javascript_semantics` 等证据追踪。它们消费已产生的证据；返回未知或部分覆盖时不能补写成确定结论。
- 文档区分目录/ASAR 静态入口和其他入口。后续分析公开网页脚本时应先形成最小目录及来源清单，不把一个 JS 文件随意交给通用原生二进制路径。
- 原生深度分析依赖具体 provider、目标格式与装载条件；[.NET 指南](D:/Project/rea/docs/managed-code-analysis.md)只证明相应托管格式的工具范围。此前 .NET 样例成功不证明 NDS、GBA、Switch 或某个游戏包已经兼容。

上次工具链与云端检查保存在[环境记录](../../工作环境/REA与CodexCloud.md)。它们是当时的运行证据，不是对任意新目标的承诺；云端没有因此获得全部原作分析引擎。

## 候选任务，按价值而不是按工具安排

### 优先候选：一条普通招式从资料到执行

- 问题：PokéBonk 如何把来源招式变成可执行攻击？共同逻辑和单招例外分别在哪里？
- 已有依据：本地[招式适配研究](../../pokebonk/招式适配与融合系统.md)记录了公开客户端静态锚点，核查日期为 2026-10-25。
- 缺少输入：本次要分析的确定构建、原始模块内容与摘要；旧压缩变量名不能直接视为新版本接口。
- 最小工作：选择一招普通直线攻击和必要依赖；已有文本足够就给出定位，跨模块关系不清才调用 REA。
- 交付：资料字段 → 选择条件 → 执行函数 → 范围/目标/效果的可定位链路，分别列观察与推断，说明还未运行的部分。
- 结束条件：回答这个具体问题，或明确工具覆盖/动态条件导致无法回答。不要扩成所有招式的全量逆向。

### 后续候选：一个实例的保存与恢复

- 问题：某个招式或伙伴实例哪些字段进入保存，重新载入时从哪里恢复？
- 已有依据：融合构造与槽位替换有静态笔记，完整跨局保存路径仍未知。
- 交付：字段与读写位置、重建流程、未知条件；静态观察不直接声称重新载入行为已验证。
- 优先级：本作需要对照某个保存问题时再开展；本作自身存档规则照常设计。

### 条件候选：原作的一项未解机制

- 先写出作品、平台、地区/修订和一个问题，如某次行动推进、招募初值或一个状态结算顺序。
- 先查 pmd-red、pmdsky-debug 等既有内容。只有缺口确实需要二进制时，才确认可用样本、目标摘要、对应符号及工具装载能力。
- 当前没有指定样本，不开展广泛原作扫描，也不把缺样本说成游戏项目无法继续。

### 延后项

融合全链路、Z 晶/Mega 扩展、Arena 2D 未公开客户端、整套资源提取、作者内部开发管线推断，不列入首个 REA 任务。公开更新可以提供变更线索，不能证明作者实际用了什么内部工具。

## 交付给游戏路线的报告格式

每份结果只需包含以下内容：

1. 具体问题与消费它的游戏决定。
2. 目标、版本/构建、样本摘要和来源；缺样本就明确说明。
3. 使用的读取/静态/运行观察方式及实际覆盖。
4. 观察结果，带文件、函数、偏移或 REA 证据标识。
5. 从观察推导的解释、未知与可反驳条件；静态与实际运行分别标明。
6. 对本作的参考价值和不能直接照搬的部分。
7. 是否已回答问题；如未回答，下一项最小必要输入是什么。

REA 结果不直接写入游戏规则或内容数据。游戏路线在自己的决策记录中说明采用、改编或不采用及理由，普通结果引用即可完成衔接。
