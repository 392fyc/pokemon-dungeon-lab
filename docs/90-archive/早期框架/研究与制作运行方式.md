# 研究与制作运行方式

本项目已合入两轮研究基线，当前按[从研究到试开发的阶段路线图](../试开发/从研究到试开发的阶段路线图.md)组织工作。先交试开发准备包，获准后制作运行骨架与单层可玩片段，再用真实体验决定后续范围；本轮没有开始游戏实现。本文说明通用职责和制作流程，阶段顺序与完成条件只在路线图维护。

## 审核版本与会话职责

当前研究基线为PR #2合入提交9ca775a；[v0.1](../审核版本/v0.1-2026-10-25/审核入口.md)及[v0.2](../审核版本/v0.2-2026-10-25/审核入口.md)保留历史身份。按[游戏项目路线](游戏项目路线.md)与[REA辅助研究路线](REA辅助研究路线.md)分工，复用本库而不复制两套玩法决策。主会话维护阶段和当前决定，两云提交独立结果，由主会话整合。

现成 Showdown 数据、公开素材格式与已有源码先直接研究。只有影响具体游戏决定的外部实现缺口才交给 REA；工具维护不混入两条游戏交付。两边通过具体问题、带版本的证据与采用记录衔接，不新建调度服务，也不因入口已写好而自动创建或派发新会话。

## 本项目已有的基础与仍需制作的部分

| 输入 | 可复用的部分 | 本作需要补的部分 |
| --- | --- | --- |
| Pokémon Showdown | 已选作为物种、招式、特性与学习资料来源 | 固定版本和世代，筛选与身份映射，地牢射程、遮挡、回合与特性适配 |
| SpriteCollab / PMDO 格式资料 | 角色图像参考、方向与动作格式、导入经验 | 来源逐项确认、脚底基准、图集转换、缺动作与本作特效 |
| PokéBonk 研究 | 共用行为、单招覆盖、配方与发布后交互修复的组织经验 | 本作行动回合、队伍、撤离与救援规则 |
| Arena 2D 研究 | 已确认的像素角色、地形层次和演出偏好 | 本作场景比例、镜头、范围提示与素材规格 |
| Phaser 4 + TypeScript | 已完成引擎路线决策 | 游戏工程、规则实现、浏览器与 Windows 交付尚未开始 |
| Codex Cloud / REA / Obsidian | 已有工作环境、研究入口与检查证据 | 后续按任务同步最新裁决，再完成具体运行验证 |

因此，工作重点是“复用可用来源，适配已有格式，补齐本作规则”。取得数据库、图像或一段可参考实现，不等于已经取得完整可运行的游戏。

## 当前采用的协作顺序

1. **读当前裁决与已有材料。** 主代理先读总索引、当前决策和相关主题，固定本次要解决的问题。遵守行动推进回合、探险次数计期限、等级解锁高风险高收益任务并由玩家选择等已明确方向；对主副、招募和委托的其他提案，保留其归属并比较必要细则。
2. **只调查缺口。** 一手研究回答来源确实做了什么；源码阅读回答可以复用什么。无法核实的制作方式保留未知，不编造效率结论。
3. **形成少量具体补充方案。** 主代理把候选写成玩家局面、输入、结算结果与取舍。例如比较“全灭也推进救援”和“只有成功才推进”，不重新生成六套完全不同游戏。
4. **独立检查会改变结果的反例。** 对招募、全灭、收费、等待和回归这类相互影响的规则，安排一名独立审查者核对用户要求、例子和遗漏。简单文字修订不强制重复整个代理链。
5. **把需要决定的事项收进当前阶段交付。** 试开发的临时基准、范围与授权一起放入准备包；完整经济未进入本片段时不提前要求逐项定价。已授权的检索、文档维护和常规技术选择自主完成。
6. **写出可执行的短规格。** 引用唯一规则表，补本次输入、触发、对象、顺序、保存和界面；临时参数如实标明。规则可执行且必要边界有据后停止泛化补例。
7. **获准后完成一段可操作体验。** 先打通运行与保存，再接入单层探索、战斗、邀请、正常或失败结果及恢复；完整走失、付款、回归和培养在下一段范围中安排。实现正确、实际体验和发布分别判断。

已有 Mercury / SoT 职责材料和一手救援案例可复用；涉及永久失去、自由编队、双重计数与物资经济交互时，按实际改动做独立检查。用户对方向的明确澄清由主代理同步关联笔记并核对，不为文字同步重复整套研究。研究与检查在本项目完成。

## 数据、素材与功能的制作管线

- **数据：** 固定来源 → 选定内容范围 → 身份映射 → 地牢行为适配 → 缺项清单 → 规则检查。Showdown 不自动决定本作招募或救援。
- **素材：** 来源与使用条件 → 动作、方向与偏移审阅 → 转换小样 → 运行场景检查 → 扩充角色。参考截图和可投入的原始素材分别标记。
- **系统：** 用户框架 → 补充细则 → 反例与状态检查 → 用户裁决 → 实现 → 持久化、交互和完整局体验验证。
- **新增内容：** 先判断是填已有行为参数、补一个例外，还是增加新行为；只有新行为才扩大底层验证范围。

对伙伴与救援系统，短规格需连接伙伴实例与初始保护身份、参战名单与探险结算标识、招募事件、公开目标完成事件与新增跨局成果、未付费期限与已付费等待、报价和基地收入、物品所在容器及失败归属。资料来源与本作规则分别记录；Showdown 不提供本作救援规则。这些是候选数据职责，不是已创建的程序接口。

本轮研究到未来实现的交付应包含：已选约束清单、仍待裁决的规则、池内状态与结算顺序、等级与物资方案、连续失败和临界到期例子。先把一条规则的这些信息放在关联主题内，不为每种字段另建任务或数据库。

## 持续研究的推进方式

用户允许长线研究，并要求减少频繁停止询问。已允许的 B 候选是当前研究起点；主代理自主完成相关资料核查、方案比较、关联文档维护与必要的独立反例检查，按完整议题交付。候选保留不等于实装授权或平衡认可。

已有研究足以进入试开发准备包。按[阶段路线](../试开发/从研究到试开发的阶段路线图.md)收敛伙伴选择、操作负担和新信息三个主问题；只补阻碍规格执行的空白，不反复补证明趣味的纸面路线。完整培养、经济、连续区域及扩展内容保留在[远期范围](../../06-研究/玩法研究/分阶段范围与扩展顺序.md)，不重跑全量市场考察。

用户已说明文档维护与当前工作阶段是默认背景，常规答复不重复提醒；只在范围实际改变或产生交付风险时说明。

常规数值样例、文档分类和技术取证可自主推进并标明假设。需要改变用户已选方向、改变范围或进行不可逆外部操作时，才集中说明实质分歧；不把每个目标数量或分钟区间变成一次确认。继续研究不自动宣称已有后台持续执行。

## 初期阶段的交付与边界

当前交付是阶段路线方案；准备包、运行骨架、可玩片段和体验复盘均有独立完成条件。尚未采纳的玩法与数值保留候选身份。规则的纸面一致性检查不代表已经好玩。

近期片段记录伙伴选择理由、无效行走、切主控、草稿误解和实际恢复。完整经济接入后，才进一步观察二人恢复、走失、委托负担和等待；这些不是单层试开发的通过条件。浏览器运行检查与Windows原生程序验收分开，后者尚未进入本段。

暂缓自建编排器、固定多轮双模型审查、常驻监控、多 lane 注册与跨仓模板同步。开始实现后，按游戏仓当时约定使用清楚的任务范围、隔离分支、相关检查和必要审查；不预先复制另一项目全部流程。
