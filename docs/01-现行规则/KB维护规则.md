# KB 维护规则

本库（仓库的 `docs/`，同时是 Obsidian vault）遵守 Mercury `kb` 包的通用约定（`.mercury/packs/kb/docs/kb-conventions.md`）。本页只写本项目在通用约定之上的专属规则。规则编号 K1、K2…，改动规则时在同一个 PR 里更新本页并在[决策登记](../03-决策/决策登记.md)登记。

为什么要这些规则：KB 会以两种方式失效，而多写文档治不好它们。一是代理找不到什么是现行的；二是过时的文字还放在看起来像现行的位置。2026-10-31 的检查发现，本库这两种情况都有。入口页停在 10-29，还写着“尚未开始实现”；7.8 改掉的等级规则在旧规格里没有任何标注。下面的规则就是为了让这两件事不再发生。

## K1 分级结构

| 目录 | 放什么 | 一句话判断 |
| --- | --- | --- |
| `01-现行规则/` | 游戏现在怎样运作、本页（项目目标与范围类决定在决策登记） | “现在是这样” |
| `02-进度/` | 唯一的进度页；`计划/`、`自测记录/` | “做到哪了” |
| `03-决策/` | 决策登记 | “谁在什么时候定了什么” |
| `04-规格/` | 里程碑变更单 | “这一轮要改什么、为什么” |
| `05-制作流程/` | 数据与素材的现行流程和登记 | “内容怎样进游戏” |
| `06-研究/` | 决策之前的调查与纸面推演、参考作品 | “我们查到了什么” |
| `07-工作环境/` | 代理与 lane 怎样工作 | “谁怎样干活” |
| `90-archive/` | 历史：试开发、早期框架、冻结审核材料 | 不作为工作依据 |

- 根目录只放入口 `README.md`。每个目录都有 `README.md` 索引，列出本目录每篇文档及其状态。
- 新文档放进最贴切的目录，并在同一个 PR 里给该目录索引加一行。不新建一级目录；确有需要时先改本页。
- 文件名按主题起，日期放在末尾（如 `研究汇总-2026-10-27.md`）。不以日期开头，因为检查脚本会把数字开头当作排序编号，判定为重复。

## K2 状态

状态只写在目录索引的“状态”列，取值为现行、草稿、已取代、历史。

- **已取代：** 索引的“取代者”列链接到替代它的文档；文档开头加一行引用块，写明现行内容在哪、哪天、哪个 PR 取代的。
- **研究目录里的“现行”**：指仍是未实现系统的设计依据（如无尽迷宫、探险队等级），不表示规则已定。

## K3 读取顺序

代理开工时按这个顺序读，读到够用为止，不扫全库：

1. 入口 [README](../README.md)；
2. [进度](../02-进度/进度.md)；
3. [游戏规则](游戏规则.md)中与任务相关的节；
4. [决策登记](../03-决策/决策登记.md)中与任务相关的行；
5. 任务 Issue 里“KB to read”列出的规格或研究；
6. 需要细节或历史时，再进入对应规格、研究或归档。

仓库根 `AGENTS.md` 的读取说明指向这里。

## K4 随任务更新

每个 PR 都按改动类型更新对应文档，并在 PR 描述里写一行 `KB:`，列出更新了哪些文档，或写“KB: no impact”并说明原因。PR 还要引用它的 Issue（`Refs #N`），否则 `guard.ps1 pre-merge` 会拒绝合并。

| 改动 | 同一个 PR 里要做的 |
| --- | --- |
| 改了游戏规则或数值（包括 main 的工作值） | 改[游戏规则](游戏规则.md)对应条目；在决策登记加一行，被取代的旧行改为“已取代”；受影响的规格或研究改状态并加取代说明 |
| 里程碑合并或状态变化 | 改[进度](../02-进度/进度.md)的里程碑表、已知问题和下一步 |
| 新里程碑开工 | 在 `04-规格/` 写规格，状态“草稿”；在 `02-进度/计划/` 写计划（需要时） |
| 规格合并且实现完成 | 把结论收进游戏规则；规格状态改为“已取代”，取代者是游戏规则 |
| 写了自测或长测记录 | 放进 `02-进度/自测记录/` 并在索引加一行（状态“历史”）；进度页引用它 |
| 新研究 | 放进 `06-研究/` 对应子目录，并在索引加一行 |
| 用户做了新决定 | 在决策登记加一行，决定者写“用户”，来源链接到保存原话的文档 |

## K5 规格的生命周期

草稿（开工时写）→ 合并（实现完成）→ 收编进游戏规则 → 已取代。

规格保存当时的用户原话、扫描数据和审查修正，是细节与历史依据；游戏规则只写结论。收编时，游戏规则的条目注明来源决策编号，并链接规格的具体小节，方便查细节。

## K6 决策

- **决定者分两种：**
  - 用户：附原话的来源；
  - main：代理按授权定的工作值，用户可随时改。

  不能把代理的推导写成用户决定。
- **新决策取代旧决策：** 旧行状态改为“已取代”，并写明取代者。不删除旧行。

## K7 冻结与归档

- `90-archive/trial-spec/`、`90-archive/审核版本/` 中的原文件，以及 `docs/.gitattributes` 里标为 `-text` 的文件，保持原字节，不改正文，搬家也不改。只允许新增 README 索引。
- 例外：`trial-spec/README.md` 在 2026-10-31 末尾追加了索引节，原字节可按 `source-manifest.json` 中的 SHA 从 Git 历史核对。
- 归档以外的索引只链接 `90-archive/README.md`，不直接链接归档里的文档。现行文档的正文需要引用历史时可以链接。

## K8 写作

- 简体中文，按费曼方式写：外行也能看懂，定义术语，给出例子或证据。
- 区分以下几类内容：
  - 用户决定与代理推断；
  - 实测与纸面推算。
- 库内用相对链接。提到 `docs/` 以外的仓库文件，写代码格式的仓库相对路径，不写 Markdown 链接，因为 Obsidian 只能打开库内文件。
- 代理直接编辑任务 worktree 中的文件，与代码一起走 PR。Obsidian 只用于浏览主 checkout，见[Obsidian 使用说明](../07-工作环境/Obsidian使用说明.md)。

## K9 检查与整理

- 每个改动 `docs/` 的 PR 都要通过：

  ```
  python -B -X utf8 .mercury/packs/kb/scripts/kb_check.py docs
  ```

  它检查索引与状态。规则是否正确由审查负责：审查者要核对改动与游戏规则、决策登记是否一致，留着现行状态却已被改动推翻的文字算作问题。
- **每个里程碑收尾时整理一次：**
  - 游戏规则超过约 250 行时删减；
  - 进度页的“已知问题”逐条核对是否仍然存在；
  - 把已完成的规格改为“已取代”。
